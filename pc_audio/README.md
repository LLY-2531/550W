# pc_audio · MOSS 的听觉大脑

《流浪地球 550W》复刻项目的 **PC 端音频程序**。它读电脑麦克风，判断
「有没有人在说话 / 有没有响声」，然后把结果通过串口推给 ESP32 —— 让 MOSS 竖起耳朵。

**对应真机上的 INMP441 数字麦克风**：真机是 ESP32 自己采音，这里先让电脑采，
把「听没听见」的结论用串口告诉 ESP32。逻辑调通之后，把这一段搬进固件即可，
**串口协议完全一致，ESP32 那边一行都不用改**。

## 一、装环境（只做一次）

在 VS Code 里打开 **这个文件夹**（`pc_audio`），然后 `` Ctrl + ` `` 开终端：

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

装完终端提示符前面会出现 `(.venv)`。**没看到 `(.venv)` 就说明还在用系统 Python。**

> 注意：`pc_audio` 和 `pc_vision` 各有自己的 `.venv`。因为音频不需要 OpenCV，
> 分开装可以让两边互不干扰。用哪个程序就激活哪个目录的虚拟环境。

## 二、先让它跑起来（不需要麦克风、不需要硬件）

```bash
python moss_audio.py --source demo
```

终端会出现一条**电平条**在动，下面同时打印 JSON：

```
[==------|---------------------]   -64.8 dB  底  -64.6  门限  -50.0  IDLE
[========|#############--------]   -17.0 dB  底  -64.6  门限  -50.0  CLAP
[================================]   -13.3 dB  底  -64.6  门限  -50.0  LISTEN
```

合成音频按 **3.2 秒一轮**循环：**安静 → 拍手 → 说话**。所以你会看到
`IDLE` → `LISTEN` 反复切换，中间还夹着一瞬 `CLAP`。

按 **Ctrl + C** 退出。

> 电平条的读法：`-` 是静音区，`#` 是「有声音但没到判定门限」，`=` 是超过门限的部分，
> `|` 标出门限落在哪。门限 = 噪声底 + 信噪比门限（下面会讲）。

## 三、接上真麦克风

```bash
python moss_audio.py
```

然后**说句话、拍拍手**，你会看到它切到 `LISTEN`、`text` 变成 `hearing` 或 `clap!`。

### 万一没反应：用 `--probe` 先确诊

Windows 上一个麦克风常常同时挂在 **MME / DirectSound / WASAPI / WDM-KS** 四套接口下，
而**其中有些接口会给出「数字静音」**（一直是 -96 dBFS，读到的全是零）。
这时你会以为"麦克风坏了"，其实只是选错了接口。

```bash
python moss_audio.py --probe
```

它会把每个输入设备挨个试听 0.4 秒，按实际音量排序，直接告诉你该用哪个：

```
排名   编号    名称                      接口              RMS dBFS
1    18    电脑扬声器 (Realtek ...)   Windows WDM-KS     612.8  ← 假值/静音，忽略
3    25    麦克风 (TANCHJIM BUNNY DSP)  Windows WDM-KS     -59.0
6    1     麦克风 (TANCHJIM BUNNY DSP)  MME                -95.9
...
  ✔ 建议使用：--device 25    （麦克风 (TANCHJIM BUNNY DSP) · Windows WDM-KS）
```

**这个项目在这台电脑上的实测结论**：只有 `--device 25`（WDM-KS 那条路径）是真信号，
MME / DirectSound 全是数字静音。这属于真实故障，别以为是自己代码写错了。

嫌每次指定麻烦，就加 `--auto`，让程序每次自己试听、自己挑：

```bash
python moss_audio.py --auto
```

> `--probe` 里那些标着「假值/静音，忽略」的行，是驱动 bug 报出的荒谬读数
> （比如 612.8 dB、-180 dB）。程序会自动排除它们，不会误选。

## 四、接上 Wokwi 仿真（零硬件也能让 MOSS 反应）

1. 确认 `wokwi.toml` 里有 `rfc2217ServerPort = 4000`（阶段 7 已加好）。
2. VS Code 里 `F1` → **Wokwi: Start Simulator**，**保持仿真面板可见**。
3. 另开终端：

   ```bash
   python moss_audio.py --source demo --port rfc2217://localhost:4000
   ```

4. 仿真里的 MOSS 会跟着切状态：`LISTEN` 时灯变青绿、OLED 显示 `hearing`；
   拍手瞬间显示 `clap!`；安静下来回 `IDLE`。

## 五、它是怎么判断「有没有声音」的

这是这一步最值得理解的地方，一共三层：

### 第 1 层：音量怎么算 —— RMS → 分贝

每一「块」声音（默认 1024 个采样点，约 64 毫秒）算一次均方根：

```
rms   = sqrt(mean(x²))            # 平均能量
dBFS  = 20 × log10(rms)           # 转成分贝，0 是满刻度，越小越安静
```

- 安静房间：约 **-60 dBFS**
- 正常说话：约 **-30 dBFS**
- 拍手：峰值能到 **-10 dBFS** 以上

### 第 2 层：噪声底怎么定 —— 滚动窗口的低分位数

**这是最容易做错的一步。** 房间本底噪声会变（开空调、开风扇），所以门限不能写死。
但如果用平均值或指数平滑，人一说话、啪一下拍手，噪声底就被抬上去了，
接下来反而听不出差别 —— 我在调试时就踩了这个坑：第一版程序里，
开局那记拍手把噪声底顶到 -17 dBFS，结果后面整段"说话"全被判成安静。

**正确做法**：取最近 4 秒音量的 **10% 分位数**。把最近的音量从小到大排队，取第 10% 名那个值 ——
它大概率落在"没人说话的那些瞬间"，于是天然抗干扰。

另外，判定为**拍手的那种瞬态块不进窗口**，免得把本底抬上去。

### 第 3 层：判定 —— 两个门限都要过

```
有声音 ⟺ 电平 ≥ --db-th(-50 dBFS)  且  电平 − 噪声底 ≥ --snr-th(8 dB)
```

- `--db-th` 绝对门限：防止在极安静的房间里，一点点杂音就算"有声音"
- `--snr-th` 相对门限：让它在吵一点的环境里也能灵敏工作

### 顺带：拍手检测

拍手是**短促爆音**，特征很明显：峰值很高、前一块很安静。

```
峰值 ≥ --clap-th(-12 dBFS)  且  前一块峰值 < clap-th − 12
```

拍手会**绕过防抖动**立刻响应（因为它是"事件"，不是"状态"）。

## 六、全部参数

| 参数 | 说明 | 默认 |
|---|---|---|
| `--device` | 输入设备，填编号或名字的一部分 | 系统默认 |
| `--list` | 列出所有音频设备后退出 | — |
| `--probe` | 逐个试听所有输入设备、按音量排序后退出 | — |
| `--auto` | 自动试听并挑一个真正有信号的设备 | 关 |
| `--source` | `mic`=麦克风 / `demo`=合成音频 / 路径`.wav` | `mic` |
| `--samplerate` | 采样率（设备不支持会自动退回默认值） | `16000` |
| `--blocksize` | 每块采样点数，决定反应快慢 | `1024` |
| `--db-th` | 绝对门限 dBFS | `-50` |
| `--snr-th` | 信噪比门限 dB | `8` |
| `--clap-th` | 拍手判定门限 dBFS | `-12` |
| `--no-clap` | 关掉拍手检测 | 关 |
| `--port` | `COM3` 或 `rfc2217://localhost:4000`，不给就不发 | 无 |
| `--stable` | 连续 N 块一致才切状态，防抖动 | `3` |
| `--heartbeat` | 状态不变时每隔几秒也输出一行 JSON | `2.0` |
| `--no-meter` | 不显示终端电平条 | 关 |
| `--frames` | 只跑 N 块就退出（自测用） | `0`（一直跑） |
| `--verbose` | 每一块都输出 JSON | 关 |

## 七、它和固件之间的"暗号"

| 发出去的 | ESP32 收到后 |
|---|---|
| `MODE LISTEN` + `TEXT hearing` | 进入「在听」状态（青绿灯声波 + 微幅抖动） |
| `MODE LISTEN` + `TEXT clap!` | 同上，OLED 第三行显示 `clap!` |
| `MODE IDLE` + `TEXT quiet` | 回待机（蓝灯慢呼吸） |

和视觉程序用的是**同一套协议**。所以以后想同时接视觉和音频，只要把它们的结果
融合一下再发出去就行，固件依然一行都不用改。

> `text` 用的是**稳定标签**（hearing / quiet / clap!），不是实时 dB 值。
> 因为实时 dB 每块都在变，拿它当 text 会让串口每个块都发一次、OLED 也一直在闪数字。
> 精确的电平放在 JSON 的 `dbfs` 字段里，给日志和上位机分析用。

## 八、排错

| 现象 | 原因 | 修法 |
|---|---|---|
| 一直 `IDLE`，怎么说话都没反应 | 选到的设备是"数字静音"接口 | `--probe` 找出真设备，或加 `--auto` |
| `Error opening InputStream: Invalid device` | 该接口在此设备上不可用 | 换 `--device`，或加 `--auto` |
| `Device unavailable` / 打不开 | 麦克风被别的程序独占 | 关掉会议软件 / 录音软件 |
| 报「设备不支持 16000Hz」 | 设备原生只跑 44100 | 正常，程序会自动退回默认采样率 |
| 状态疯狂跳动 | 门限太敏感 | `--stable` 调大，或 `--snr-th` 调大 |
| 总要很大声才有反应 | 门限太保守 | `--db-th` 调到 -55，或 `--snr-th` 调到 5 |
| 安静时也一直 `LISTEN` | 环境太吵 | `--snr-th` 调大（如 12） |
| `ModuleNotFoundError: sounddevice` | 装到了系统 Python | 确认终端有 `(.venv)` 再 pip install |
| 想彻底排查系统麦克风 | — | Win 设置 → 隐私和安全性 → 麦克风 → 打开「允许应用访问麦克风」 |

## 十、实测记录（2026-10-11）

| # | 测什么 | 命令 | 结果 |
|---|---|---|---|
| 1 | 合成音频 | `--source demo --frames 200` | ✅ 3.2 秒一轮：`quiet` → `clap!` → `hearing` → `quiet` |
| 2 | 设备探测 | `--probe` | ✅ 正确排除 612.8 dB / nan 两个假值，推荐 25 号设备 |
| 3 | 真实麦克风 | `--auto --frames 900` | ✅ 自动选中 25 号，回退 44100Hz，读到真实环境音 -59 dBFS |
| 4 | 串口链路 | `--source demo --port rfc2217://localhost:4000` | ✅ 对端完整收到 `MODE IDLE`/`TEXT quiet`/`MODE LISTEN`/`TEXT clap!`/`TEXT hearing` |
| 5 | `.wav` 文件源 | `--source _test.wav` | ✅ 时间点全对（2s 静音 → 拍手 → 3s 说话 → 静音） |
| 6 | 边界情况 | 设备名不存在 / wav 不存在 / 串口连不上 | ✅ 全部友好报错或降级，不崩溃 |

**这次调试踩到的两个真坑**（都已修）：

1. **噪声底被瞬间大声带偏** —— 原来用指数平滑，开局那记拍手把噪声底顶到 -17 dBFS，
   导致后面整段说话全被判成安静。改成「滚动窗口 10% 分位数 + 瞬态不进窗口」后正常。
2. **`text` 变化被吞掉** —— 原来只在 `mode` 变化时才上报，导致拍手之后说话段的
   `clap!` → `hearing` 这次变化发不出去。改成同时比较 `mode` 和 `text`。

**这台电脑的音频环境结论**（换机器可参考这个排查思路）：

- 默认输入「麦克风 (TANCHJIM BUNNY DSP)」在 MME / DirectSound 路径下是**数字静音**（-96 dBFS）
- **只有 WDM-KS 路径（`--device 25`）有真信号**（-59 dBFS，有 11 dB 波动）
- 设备原生只支持 44100 Hz，不支持 16000 Hz
- 房间本底很安静（20 秒内稳定 -59~-60 dBFS），需要真实声响才能触发 `LISTEN`
