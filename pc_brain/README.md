# MOSS 多模态大脑（阶段 9–19）

> 流浪地球 550W 复刻项目 · PC 端大脑
>
> 📖 **想直接跑起来看效果 → 看 [`DEMO.md`](DEMO.md)（演示与操作手册）**：
> 一条命令能演示什么、要启动什么、要说什么，以及"没有麦克风怎么演示耳朵"。
> 本文是**设计文档**，解释每一层为什么这么写。

> 阶段 9：把「眼睛」（摄像头）和「耳朵」（麦克风）**合成一个判断**。
> 阶段 10：给它一张「嘴」—— 把状态变成一句人话（`mind.py`）。
> 阶段 11：给它一副「嗓子」—— 把那句话**真的念出来**（`voice.py`）。
> 阶段 12：给它**真正的理解力** —— 听懂你说了什么，然后回答你（`asr.py`）。
> 阶段 13：给它**记忆和双手** —— 跨会话记住你（`memory.py`），
>          还能调工具去查时间/天气、主动记事（`moss_tools.py`）。
> 阶段 14：让那双"手"**真的能动** —— 你说"把灯变红"，灯环就红
>          （`moss_actuators.py` + 固件新增 `LED/SPIN/BEEP/STOP/PING`）。
> 阶段 15：教它**什么时候不用答应** —— 先说「MOSS」再说话（`wake.py`）。
> 阶段 16：教它**自己动一下** —— 有人来就转头看你，人走了转回来（`behave.py`）。
> 阶段 17：让它**一边说一边听** —— 把自己扬声器的声音从麦克风里减掉，
>          于是它念台词时你也能插嘴（`aec.py`）。这一步之前它是"半个聋子"。
> 阶段 18：给它**真正的眼睛** —— 从"瞧见有人/有动静"升到"认得出杯子、键盘、人"，
>          于是你问"画面里有什么"，它答得上来（`vision.py`）。
> 阶段 19：让它**自己注意到变化** —— 桌上多了个杯子，不用你问它也会说
>          （`presence.py` + `behave.py`）。难点不是"看得出变化"，
>          而是**别把检测器的抖动当成变化**。

## 一、它解决什么问题

阶段 7、8 各有一个独立程序，但有两个毛病：

1. **各跑各的**：视觉不知道听觉在听什么，反之亦然。看到人不会因为"他在说话"而升级反应。
2. **抢同一个串口**：两个程序都要连 `rfc2217://localhost:4000`，同一时刻只能开一个。

`moss_brain.py` 把两路信号合成**一条串口输出**，从此只跑这一个程序就够了。

## 二、架构：五条线程 + 一个融合循环

```
┌──────────────────┐         ┌──────────────────────────┐
│  视觉线程        │         │  听觉线程                │
│  CameraScene     │         │  MicSource               │
│  ├ 【18】目标检测│         │  ├ 【阶段17】AEC 减回声  │
│  ├ 【19】在场跟踪│         │  ├ 音量 dBFS / 自适应噪声底│
│  └ 运动检测      │         │  ├ 拍手检测              │
│     ↓ 快照(加锁) │         │  └ 切句 UtteranceSegmenter│
└────────┬─────────┘         └─────────┬────────────────┘
         │                             │ 一整句音频
         │                             ▼
         │                   ┌──────────────────┐
         │                   │ 识别线程 AsrWorker │ → whisper / API
         │                   │  声音 → 文字       │
         │                   └────────┬─────────┘
         │                            │ heard 文本
         ▼                            ▼
         ┌────────────────────────────────────┐
         │  主循环 20Hz 融合                   │   ← fuse() 一张优先级表
         │  防抖动（连续4次）                   │◄────┐
         └───┬────────────┬───────────────┬───┘     │ speak.busy()：说话时按静音
             │            │               │         │ 【阶段17】只在拿不到参考信号时
    状态变了  │            │ 状态变了(异步)  │ 听懂了一句话 │ 才这么干；否则交给 AEC
             ▼            ▼               ▼
   ┌──────────────┐  ┌──────────────────────────┐
   │ MODE 立刻发   │  │  语言线程 MindWorker       │ → 大模型
   │ TEXT 先占位   │  │  有人说话→回答 / 没人→汇报   │
   └──────┬───────┘  └────────┬─────────────────┘
          │                   │ 想好了补发 TEXT <tag>
          │                   ▼
          │           ┌──────────────────┐
          │           │ 语音线程 SpeakWorker│ → edge-tts / SAPI
          │           │  合成 + 播放       │   → 音箱出声
          │           └────────┬─────────┘
          └─────────┬─────────┘
                    ▼
         ┌────────────────────┐
         │  一条串口 MODE/TEXT │  → ESP32（真机 COM3 / Wokwi rfc2217）
         └────────────────────┘
```

**为什么必须用线程**：摄像头 `read()` 会阻塞约 33 毫秒（30fps），麦克风
`read()` 也会阻塞，大模型一次请求可能几百毫秒，TTS 合成要 1.7~2.9 秒，
语音识别要 0.2~1.5 秒。如果串行做，等画面的这段时间就漏掉了声音、
等大模型/合成/识别时整个设备都僵住。所以五件事各一个线程：

| 线程 | 频率 | 职责 |
|---|---|---|
| VisionWorker | ~30 Hz | 读画面；**运动检测每帧都做**、**目标检测每 3 帧一次**（阶段 18，两者代价差 10 倍）；检测结果喂给**在场跟踪器**（阶段 19）滤成稳定计数 |
| AudioWorker | ~15 块/秒 | 读声音、**减掉自己的回声（阶段 17）**、算音量与拍手、**把音频切成一句句**（阶段 12） |
| AsrWorker | 事件驱动 | 把"一整句音频"变成文字（阶段 12） |
| MindWorker | 事件驱动 | 状态一变/听懂一句，就想一句台词；**顺带执行工具**（阶段 13） |
| SpeakWorker | 事件驱动 | 把台词合成成声音并播出来（阶段 11） |

**阶段 13 加的两个东西不是线程**，它们是**被 MindWorker 使用的两样外部资源**：

```
                    ┌──────────────────────────┐
   MindWorker ─────►│ ToolBox（moss_tools.py）  │ 模型说"我要调 get_time"
        ▲           │  ├ get_time / get_weather │ → 本地真执行
        │           │  ├ look / stats           │ → 结果塞回去再问一轮
        │ 事件里带   │  └ remember/recall/forget │
        │ facts +   └────────────┬─────────────┘
        │ dialog                 │ 读写
        │           ┌────────────▼─────────────┐
        └───────────│ MemoryStore（memory.py）  │ 对话 + 长期事实 → JSON 落盘
        每轮取快照   └──────────────────────────┘ 关掉再开还记得你
```

之所以不新开线程：工具执行本来就发生在 MindWorker 里（它已经是后台线程），
而记忆有内部锁保护、读写都是毫秒级，没必要再拆一层。

**阶段 15 / 16 加的两个东西也不是线程**，它们是主循环里的两道闸门：

```
  AsrWorker ──►[ WakeGate ]──► MindWorker      阶段 15：叫名字才放行
                    ▲
                    │ 识别出的文字
                    │
   主循环(20Hz) ────┤
                    │
       感知快照 ────►[ BehaviorEngine ]──► 串口  阶段 16：它自己想动就动
```

`WakeGate` 决定"这句话该不该理"，`BehaviorEngine` 决定"它自己要不要动"。
两者都是**纯逻辑、不碰硬件、不走网络** —— 所以都能离线跑几千帧来验证。
`BehaviorEngine` 只产出"要发什么命令"，发不发由主循环决定。

**阶段 19 加的东西也不是线程**，而是夹在视觉线程和 `BehaviorEngine` 之间的一层滤波：

```
  逐帧检测框（抖：这个杯子每 3 次漏 1 次）
        │
        ▼
  [ PresenceTracker ]   迟滞 + 个数确认 + 暖机  ── 纯滤波，不知道时间、不知道权限
        │
        │  稳定计数 {"cup": 1, "laptop": 1}
        ▼
  主循环 ──►[ BehaviorEngine ]──► 串口 / 说话
```

**为什么它待在视觉线程里，而不是主循环里**：它的门槛单位是「**检测次数**」
（连续 3 次检出才算来、连续 7 次漏检才算走），而"检测了几次"只有视觉线程知道；
主循环看到的是帧。放主循环就得把 `detect_every` 的除法抄过去一份 ——
改一次 `--vision-detect-every` 就会偷偷把"连续 3 次"变成"连续 1 次"。

**阶段 18 也没加线程、没加闸门，它换的是视觉线程里那副"眼睛"**：
把 Haar 人脸检测换成 `yolov8n` 目标检测（80 类 COCO）。这件事**完全发生在
VisionWorker 内部**，对外只有一处变化 —— 快照里多了 `objects` 列表。
调用方（`fuse()` / `look` 工具 / `BehaviorEngine`）不需要知道自己看的是
Haar 还是 YOLO，这正是当初把视觉做成"检测器接口"的用处（见五之十一）。

> ⚠️ 有一个**故意的例外**：`faces` 只统计"人"（`person` / `face`），
> 别的物体**不往里塞**。否则桌上一个杯子就会让 MOSS 以为"有人在"，
> 整条优先级表都会被带偏。

**为什么 MODE 和 TEXT 分两步发**：`MODE` 要立刻发（设备秒响应、灯和电机马上变），
而台词要等大模型。所以先切状态 + 发一个感知占位标签，几十毫秒后再补一条
`TEXT <台词>` 把它盖掉。

## 三、融合规则（`fuse()`）

从上往下，第一条命中的胜出：

| 条件 | 状态 | OLED 文字 | 含义 |
|---|---|---|---|
| 看见脸 **+** 听见声音 | **SPEAK** | `face+voice` | 有人跟我讲话，我在回应 |
| 只看见脸 | **VISION** | `face xN` | 有人在，我盯着看 |
| 只听见声音 | **LISTEN** | `hearing` / `clap!` | 有动静，我在听 |
| 只看见画面在动 | **MOTION** | `moving` | 有东西在动 |
| 什么都没有 | **IDLE** | `idle` | 待机 |

**为什么「脸 + 声」优先于「只有脸」**：有人且正在说话，是最强的交互信号，
设备应该表现为「在回答」（SPEAK），而不是傻看着（VISION）。

**拍手是"事件"**：绕过防抖动立刻响应（`clap!`），因为拍手是人主动打招呼，
延迟几百毫秒再反应就不灵了。

**【阶段 18】VISION / MOTION 两行的文字后面会挂上"还看见了什么"**：

```
VISION   face x1                        →  face x1 + cup, laptop
MOTION   moving                         →  moving + cup
```

这是**纯粹的信息增益**，不动优先级表一个字 —— "有人在"和"有人在，桌上还有个
杯子"是两个不同的认知，后者更有用。三条自我约束：

1. **只带非人的东西**。人在 `mode` 和 `face xN` 里已经说过了，再带一个 `person` 是废话。
2. **只塞进 VISION / MOTION 两个分支**。`text` 是"**这一路**为什么切到这个状态"
   的占位标签：LISTEN 是听出来的、IDLE 是没东西，往里塞物体名只会让人看不懂。
3. **最多带 2 种**。OLED 第三行一共 23 个字符（固件的 `gLine1[24]`），
   `face x1 + cup, keyboard` 恰好 23 个字 —— 再多就截断了。

> 这套状态名（SPEAK / VISION / LISTEN / MOTION / IDLE）**全部是固件里已有的状态** ——
> 阶段 9 **固件一行都不用改**，只是把两路信号合并后喂给同一套串口协议。

## 五、用法

### 1. 先跑全合成（不需要摄像头、不需要麦克风）

```bash
python moss_brain.py --demo
```

会弹一个预览窗：左上角显示当前 MODE / TEXT，底部一条音量条，画面里小球在动。
约 20 秒一个完整循环：`IDLE → MOTION → LISTEN(clap!) → LISTEN(hearing) → MOTION → IDLE`。

### 2. 接真设备（真摄像头 + 真麦克风）

```bash
python moss_brain.py --auto
```

`--auto` 会先试听所有音频设备、挑一个真正有信号的（原因见 `pc_audio/README` 第三节：
Windows 上一个麦克风挂在四套接口下，有些是"数字静音"）。

**然后站到摄像头前说话** —— 有脸时进 `VISION`，一开口就跳 `SPEAK`。

### 3. 接 Wokwi 仿真（真闭环）

```bash
# 先在 VS Code 里 F1 → Wokwi: Start Simulator，保持仿真面板可见
python moss_brain.py --auto --port rfc2217://localhost:4000
```

**预期**：你一说话，仿真里的 MOSS 切 `LISTEN` 电机开始扫；脸进画面切 `VISION`；
边看边说切 `SPEAK` 灯变紫罗兰、电机小幅抖；安静下来回 `IDLE`。

### 4. 无图形界面 / 自测

```bash
python moss_brain.py --demo --no-window --frames 400      # 跑 400 次融合就退出
python moss_brain.py --demo --verbose                      # 每次循环都输出 JSON
```

### 5. 让 MOSS 说话（阶段 10）

```bash
# 零配置：用内置模板台词
python moss_brain.py --auto --llm offline

# 接大模型（这里以 DeepSeek 为例，任何 OpenAI 兼容接口都行）
set MOSS_API_KEY=sk-你的key
python moss_brain.py --auto --llm api --model deepseek-chat

# 只测语言层，不打开摄像头/麦克风
python moss_brain.py --llm api --llm-test
```

跑起来后终端会多出一行 `[SAY]`，OLED 上则会显示那行短英文：

```
[SAY] 我看见你了。   [OLED] i see you   (api, 210ms)
      ↑ 中文台词                    ↑ 发给 OLED 的 ASCII 标签
```

### 6. 让 MOSS 出声（阶段 11）

```bash
# 音质最好（先 pip install edge-tts）
python moss_brain.py --auto --llm api --tts edge

# 离线、零额外依赖（Windows 内置语音）
python moss_brain.py --auto --llm api --tts sapi

# 只测嗓子
python moss_brain.py --tts edge --tts-test
```

加了 `--tts` 之后，`[SAY]` 行会多一个 `-> 出声` 标记，声音从音箱里出来：

```
[SAY] 我看见你了。   [OLED] i see you   (api, 210ms)  -> 出声
```

细节（为什么用 MCI、自说自听怎么处理、队列策略踩了什么坑）见 **五之三**。

### 7. 让 MOSS 听懂你（阶段 12）

```bash
# 完整形态：能听、能想、能说，而且它说话时你也能插嘴
python moss_brain.py --auto --llm api --tts sapi --asr whisper

# 第一次会提示要下模型（约 484MB，从 hf-mirror.com），下完就离线了
# 带宽紧张就先下小的：python asr.py --get-model tiny
```

> 阶段 17 起默认就带**全双工**（回声消除）：它念台词时你说"等一下"，
> 它听得见。戴着耳机跑的话加 `--aec off --no-echo-guard` 更干净 ——
> 原因见 **五之十第 5 节**。

跑起来后，终端会多一行 `[HEARD]`，然后是 MOSS 的回答：

```
[HEARD] 现在几点了   (音频1.15s, 1430ms, RTF 1.243, whisper)
[SAY] 本地时间下午三点十四分。   [OLED] time is 3pm   (api, 620ms)  -> 出声
```

> 注意 `--asr` 开着时 MOSS 会自动变成「少说多听」模式，
> 不再每隔两秒汇报一次感知 —— 原因见 **五之四第 5 节**（嘴不停 = 耳朵聋）。

### 8. 让 MOSS 认出画面里的东西（阶段 18）

```bash
# 先下模型（12.2 MB，一次就够）
python vision.py --download

# 完整形态：能听、能想、能说、能插嘴、还认得出东西
python moss_brain.py --auto --llm api --tts sapi --asr whisper

# 手上还没下模型也能试 —— 会自动降级到人脸检测，不报错
python moss_brain.py --demo

# 只想看它认出了什么（不接摄像头/麦克风）
python vision.py --image tools/assets/desk_objects.png
```

跑起来后问它「画面里有什么」，它会真的答上来：

```
[HEARD] 画面里有什么
[SAY] 我看到 1 个杯子、1 个键盘、1 个瓶子，基本静止。
```

> 阶段 9 的时候这个问题是**答不上来**的 —— 不是 `look` 偷懒，是那时的视觉层
> **根本没看出来过别的东西**，只能回答"几个人、有没有动"。见 **五之十一**。

## 五之二、语言层（阶段 10）：MOSS 的"嘴"

### 为什么一次返回两个字段

**OLED 用的 Adafruit 默认字体只有 ASCII，写汉字会显示成方块。** 可我们又希望
MOSS 说中文。所以让模型一次返回两个字段：

```json
{"say": "我看见你了。", "tag": "i see you"}
```

| 字段 | 去处 | 限制 |
|---|---|---|
| `say` | 终端（将来可接 TTS 真的出声） | 中文，10~20 字 |
| `tag` | 串口 `TEXT` 命令 → OLED 第三行 | **≤13 个 ASCII 字符** |

13 这个数字是算出来的：OLED 第三行从 x=50 开始画，128 宽的屏剩 78px，
默认字体 6px 宽 → 78/6 = 13。

### 三种后端

| `--llm` | 说明 |
|---|---|
| `off`（默认） | 不发台词，只发感知标签（阶段 9 的行为） |
| `offline` | 内置模板台词，零配置、不联网 |
| `api` | OpenAI 兼容的 `/chat/completions` |
| `auto` | 有 Key 就试 API，失败退回模板 |

**任何 OpenAI 兼容接口都能用**（改 `--api-base` 与 `--model`）：

| 服务 | `--api-base` | `--model` |
|---|---|---|
| DeepSeek（默认） | `https://api.deepseek.com/v1` | `deepseek-chat` |
| 阿里通义 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 智谱 | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-flash` |
| 本地 ollama | `http://localhost:11434/v1` | `qwen2.5:3b` |

API Key 也可以用环境变量：`MOSS_API_KEY`（或 `OPENAI_API_KEY`）。

### 关键设计：只保留最新、失败只切一次

- **只保留最新事件**：状态已经变了，旧状态的台词没有意义，直接丢掉。
- **事件带序号**：结果回来时校验序号，状态已经变了就丢弃，避免"配错状态"。
- **失败只切一次**：远端第一次出错就**永久**改用模板，后续瞬时返回。
  这一条是踩坑换来的 —— 每失败一次都要等超时（实测 2.2 秒），而状态每 1~3 秒
  就变一次，结果永远"回来即过期"，用户一句台词都看不到。切一次之后就正常了。
- **不阻塞**：`MindWorker` 独立线程，大模型慢也不会拖住 20Hz 的融合循环。

### 离线验证工具：`tools/mock_llm_server.py`

一个假的 OpenAI 兼容服务端，让 `--llm api` 这条路**不需要真 Key、不需要联网**
就能验证：

```bash
# 终端 1
python tools/mock_llm_server.py --port 8000 --verbose
# 终端 2
python moss_brain.py --demo --llm api \
    --api-base http://localhost:8000/v1 --api-key fake --model mock-1
```

`--verbose` 会把收到的 system / user 提示词打印出来，一眼就能看出
"状态有没有传进模型"。它还故意把 JSON 包在 ```` ```json ```` 代码块里，
用来验证客户端的容错解析（模型经常这么干）。

## 五之三、语音层（阶段 11）：MOSS 的"嗓子"

阶段 10 之后，`say` 只是终端里的一行**字幕**。这一步让它从音箱里出来。

```
MindWorker（想台词）──► SpeakWorker（说台词）──► Voice（合成+播放）
                            │
                            └──► busy() ──► 融合循环：说话时把听觉按静音算
```

### 1. 两个后端

| `--tts` | 说明 | 联网 | 音色 |
|---|---|---|---|
| `off`（默认） | 不出声（阶段 9/10 的行为） | — | — |
| `edge` | 微软 edge-tts 在线神经语音 | 要 | 最好，中文自然 |
| `sapi` | Windows 内置 `SAPI.SpVoice` | 不要 | 机械、发闷——**反而更像 MOSS** |
| `auto` | 先试 edge，失败**永久**退 SAPI | 首次要 | 自动 |

```bash
# 只用内置语音，零额外依赖、离线可用
python moss_brain.py --auto --llm api --tts sapi

# 音质最好的路子（需要 pip install edge-tts）
python moss_brain.py --auto --llm api --tts edge

# 单独测嗓子，不碰摄像头/麦克风
python moss_brain.py --tts edge --tts-test
python moss_brain.py --tts edge --tts-list      # 看有哪些中文音色
python voice.py --tts edge --selftest           # 合成/播放/打断全套自检
```

MOSS 的默认音色是 `zh-CN-YunxiNeural`，**语速 -10%、音调 -15Hz** ——
压低、放慢，出来就是那种冷静的机器腔。想换：`--tts-voice` / `--tts-rate` / `--tts-pitch`。

> **edge-tts 报 403 怎么办**
> 症状：`aiohttp.client_exceptions.WSServerHandshakeError: 403, Invalid response status`，
> 地址指向 `wss://speech.platform.bing.com/...`。
> 原因：微软会**周期性改服务端的鉴权算法**（`Sec-MS-GEC` token）。网络本身是通的
> （`curl https://speech.platform.bing.com/` 能返回 400/302），是服务端主动拒绝，
> 升级 edge-tts 到最新版也可能还是会 403 —— 这不是你的代码或网络的问题。
> 应对：① 换 `--tts sapi`（离线、免登录，永远不会被拒）；② 或 `--tts auto`
> 让它失败后自动退到 SAPI。等 edge-tts 上游跟进后，`--tts edge` 会自己恢复。

### 2. 播放为什么不用 ffmpeg

Windows 自带 MCI（`winmm.dll`），几行 `ctypes` 就能放 mp3：

```
open "<文件>" type mpegvideo alias moss1234
play moss1234
```

**零额外依赖**，而且 `stop` / `status mode` 都有，能"打断"、能查询播放状态
（不用靠 `sleep` 猜）。这也是为什么走"先落盘 mp3 再播"——MCI 需要一个完整文件。

### 3. 一个必须解决的物理问题：自说自听

MOSS 用音箱说话 → 麦克风立刻听见 → 大脑以为「有人在跟我说话」→ 又进 SPEAK
→ 又说一句 → 又听见……**这是正反馈，MOSS 会自己跟自己聊起来。**

所以说话期间把听觉按静音算（`SpeakWorker.busy()`），说完再留 350ms「余音时间」
（`--tts-guard`）等房间混响和音频缓冲排空。

实测对比（同样 400 次融合，合成音源）：

| | LISTEN 次数 | 正在说话时误判成「有人在讲话」 |
|---|---|---|
| 抑制**关** | 12 | 12 |
| 抑制**开** | **0** | **0** |

两条要点：
- **视觉不屏蔽** —— 说话时你走过去，它照样在 SPEAK 状态盯着你
- **默认连拍手也一起屏蔽**。麦克风分不清「你拍的」和「MOSS 自己开口那一下的爆音」，
  放着不管它会自己打断自己。真想用拍手打断，加 `--barge-in`

> 踩坑记录：一开始只改了 `dbfs`，测试发现**完全没作用** ——
> 因为 `fuse()` 读的是 `listening` 这个**已经算好的布尔值**，不是 `dbfs`。
> 必须把 `listening` 一起按下去才行。这种"改了变量但没改到真正被读的那个"
> 是并发调试里最典型的坑，只能靠 A/B 实测抓出来。

### 4. 队列策略：一旦开口就说完

`SpeakWorker` 的三条规则：

1. **队列深度恒为 1** —— 永远只存"最新那一句"，旧的直接扔
2. **一旦开口就说完**（commit）—— 只有明确打断（拍手 / 退出）才中途掐掉
3. **同一句话 3 秒内不重复念**（`--tts-dedup`）—— 防状态抖动复读

第 2 条是踩坑换来的。最初写的是「新台词立刻打断旧台词」，听着很合理，实测直接翻车：

> 合成一句要 1.7~2.9 秒。如果每来一句新台词就掐掉正在合成的这一句，
> 那么状态变化比合成还快时（`--demo` 里 0.27 秒就变一次），
> 每一句都在合成到一半被掐死 → **一句都念不出来**。
> 日志里全是「被打断丢弃 12 句」「说话 0 句」。

典型的「输入速率 > 输出速率」问题。正确解法不是拼命追最新，而是
**以输出速率说话、每次取开头那一瞬间最新的那一句**：延迟有界（最多落后一句），
但保证真的出声。改成这样之后同样的场景：`说话 4 句 · 被打断丢弃 0 句`。

### 5. 延迟是多少（实测）

| 环节 | 耗时 |
|---|---|
| 合成（edge-tts，联网） | 1.7 ~ 2.9 秒（首次连 TLS 更慢） |
| 播放（MCI） | ≈ 音频本身长度（约 3~4 秒 / 15 字，-10% 语速） |

所以从"状态一变"到"听见声音"大约 **2~3 秒**。听着像"思考了一下再开口"，对 MOSS 不违和。
**设备那边是秒响应的**：`MODE` 立刻切 SPEAK、灯和电机马上动，只有声音晚一点到。

想更快：`--tts-rate "+10%"`（语速快一倍时间减半）、或换更短的台词。

## 五之四、听觉理解层（阶段 12）：MOSS 听懂你说什么

到阶段 11 为止，MOSS 是个**广播**：它看得见你在、听得出有声音、会说人话，
但它不知道你在说什么。你问它"几点了"，它回你一句"我看见你了"。

这一步把"声音"变成"文字"，它才终于能**接话**。

```
麦克风 PCM ──► UtteranceSegmenter ──► AsrWorker ──► "现在几点了"
               （切成一整句）          （whisper）        │
                                                          ▼
                                    mind.py 提示词从「汇报状态」
                                    变成「★ 用户刚刚对你说：现在几点了」
                                                          │
                                                          ▼
                                        SpeakWorker ──► 音箱
```

### 1. 两种识别后端

| `--asr` | 说明 | 联网 | 首次要下 |
|---|---|---|---|
| `off`（默认） | 只判断有没有声音（阶段 8 行为） | — | — |
| `whisper` | 本地 faster-whisper，**离线、免费** | 只首次下模型 | 75~484MB |
| `api` | OpenAI 兼容 `/audio/transcriptions` | 每次 | 不用 |
| `auto` | 先试本地，起不来退 API | 看情况 | 看情况 |

```bash
# 本地识别（推荐）
python moss_brain.py --auto --llm api --tts edge --asr whisper

# 第一次会从 hf-mirror.com 下载模型（约 484MB），之后完全离线
python asr.py --list-models      # 看有哪些模型 / 下没下
python asr.py --get-model tiny   # 只下模型，不下就先用小的试

# 只测识别（不开语言层和语音层，省得互相干扰）
python moss_brain.py --asr whisper --asr-test

# 识别一个音频文件
python asr.py --file 录音.mp3 --model small
```

**模型放在哪**：`~/.cache/moss_asr/faster-whisper-<名字>/`，就 4 个文件
（`config.json` / `model.bin` / `tokenizer.json` / `vocabulary.txt`）。
想换地方：`--asr-dir`。

### 2. 模型从哪来（国内必看）

`huggingface.co` 在国内基本不可达，**`hf-mirror.com` 通**。所以这里
**故意不用 `huggingface_hub`**，直接从镜像拉那 4 个文件。

两个实测踩到的坑：
- **hf-hub 的 Xet 传输后端**（`hf-xet`）不经过镜像，会报 `401 Unauthorized`
  （`cas-server.xethub.hf.co`）。要绕过就得设 `HF_ENDPOINT` + `HF_HUB_DISABLE_XET`。
- 更坑的是 **hf-hub 2.2.0 在 Windows 上建快照软链会失败**，留下 **0 字节的
  `model.bin`**，报错却是 `model.bin is incomplete: failed to read a value of size 4`
  —— 缓存里明明有个 75MB 的 blob，但加载的就是个空文件，非常难查。

自己下 4 个文件，出问题一眼能看出来。这也是为什么 `asr.py` 里没有任何
`HF_ENDPOINT` 之类的环境变量魔法。

### 3. 怎么把"一句话"切出来（VAD）

连续音频流不会自己告诉你"这句说完了"。`UtteranceSegmenter` 是个状态机：

```
silence ──(连续 160ms 有声)──► speech ──(连续 700ms 无声)──► 吐出一整句
                                     └─(超过 15s)─────────► 强制切断
```

三个容易踩的点，都处理了：

| 问题 | 处理 |
|---|---|
| VAD 从"听到"到"确认"要几块，第一个字被切掉 | **前置缓冲 300ms**：环形缓冲一直在存，确认时"回到过去"取回来 |
| 说话中间一停顿就被切成两句 | 端点判定看 **700ms** 静音（`--asr-end-ms`） |
| 咳嗽、关门声也送去识别 → whisper 瞎编 | 按**有效说话时长**判（`--asr-min-ms` 默认 250ms） |

最后一条是踩出来的：一开始按"片段总长度 ≥400ms"过滤，结果 130ms 的咳嗽
被前置缓冲（300ms）+ 尾部保留（150ms）撑成了 450ms，照样通过。
**总长度不等于说话时长**，得单独统计真正有声的块数。

### 4. 为什么必须半双工（MOSS 说话时它听不见你）

这是阶段 11「自说自听」问题的加严重版。不禁的话：

> MOSS 说话 → 麦克风录到自己的声音 → 识别成文字 → 当成"用户提问" → 回答
> → 又录到自己 → ……**无限自我对话**。

彻底解法是 AEC（回声消除，从麦克风信号里减掉自己的声音），那是另一个量级的工程。
所以这里选了**半双工**（对讲机模式）：**它说话时，麦克风对它就是关着的。**
绝大多数 DIY 语音助手都是这么干的。`--tts off` 时没这个问题。

### 5. 这带来一个反直觉的后果：MOSS 必须"少说多听"

半双工 + 爱说话 = 聋子。实测第一次跑就翻车了：

> 开了 `--tts edge` 之后，MOSS 每次状态变化都说一句，一句 4 秒；
> 而状态每 2~3 秒就变一次 → 它**几乎一直在说话** → 麦克风一直被屏蔽。
> 结果：**`听懂 0 句 · 切段 0`**。一句话都没听见。

**一个嘴不停的东西，耳朵一定是聋的。** 所以 `--asr` 开着时，MOSS 自动
切换成"少说多听"（`--narrate auto` → `quiet`）：

| 什么时候主动开口 | 什么时候闭嘴听 |
|---|---|
| 有人进画面（VISION） | 待机（IDLE） |
| 有人正在跟我说话（SPEAK） | 画面有动静（MOTION） |
| 拍手打招呼（clap!） | 只是听见声音（LISTEN） |
| 出错（ERROR） | 刚说过不到 8 秒（`--narrate-gap`） |

想让它照旧絮叨：`--narrate all`。想完全安静（只在你问的时候说）：`--narrate quiet --narrate-gap 9999`。

**同理，你问完话后 1.2 秒内（`--asr-hold`）它也不会插嘴**，
否则会出现"你刚问完几点了，它先蹦一句『我看见你了』把你问题顶掉，
那句废话还要占掉 4 秒音箱时间"。

### 6. 多轮对话

`--asr-history 3`（默认）会记住最近 3 轮，压成一小段文字塞进提示词：

```
最近的对话（越靠后越新）：
  用户：你是谁
  MOSS：我是550W，行星发动机的控制中枢。

★ 用户刚刚对你说：现在几点了
请回答他（不要描述你自己的状态），10~25 字。
```

**为什么不用标准的"多轮 messages"**：我们每轮都要求模型返回 JSON，
如果把历史回答（JSON）放进 `assistant` 角色，模型很容易开始"续写 JSON"
而不是好好回答。压成纯文本放进当前这条用户消息里，更稳也更省 token。

### 7. 延迟是多少（实测）

| 环节 | 耗时 |
|---|---|
| 端点判定（等你不再说话） | 0.7 秒（`--asr-end-ms`） |
| whisper-small 识别 | **约 1.4 秒** |
| whisper-tiny 识别 | 约 0.2~0.3 秒 |
| 大模型回应 | 0.5~2 秒 |
| TTS 合成 + 播放 | 1.7 + 3~4 秒 |

**小声说：whisper 有个固定的 1.4 秒开销**，和音频长短基本无关
（它永远按 30 秒的窗口跑编码器）。实测 5.62 秒的音频 1.48 秒、
1.15 秒的音频 1.43 秒 —— 几乎一样。所以别指望"短句子识别更快"。

想让对话更跟手：`--asr-model tiny`（快 5 倍，但中文会偶尔听错字）。
默认 `small` 是准确率和速度的平衡点。

### 8. 没有麦克风怎么验证

两个工具，都不需要硬件：

```bash
# ① TTS → ASR 闭环：自己造语音，喂进去，看能不能原样认回来
python tools/asr_roundtrip.py --model small --keep-wav _test.wav
#    因为知道标准答案，所以这还是准确率测试，不是"能跑就行"

# ①b edge-tts 挂了（报 403）时，改用本地录音当音源，一样能测
python tools/asr_roundtrip.py --from-files a.mp3,b.wav \
    --text "第一句的标准答案|第二句的标准答案" --model small
#    --from-files 与 --text 一一对应，顺序不能乱

# ② 假 ASR 服务端：不用下模型、不用联网就能验证 --asr api 这条路
python tools/mock_asr_server.py --port 8010 --verbose
python moss_brain.py --demo --asr api \
    --asr-api-base http://localhost:8010/v1 --asr-api-key fake
```

`tools/mock_asr_server.py` 还会**真的把收到的 WAV 拆开量时长**，
所以能看出"整句话是不是都切进来了"，而不是只回一句敷衍的话。

`--from-files` 这条路是专门为「合成服务不可用」准备的：edge-tts 依赖微软在线服务，
会**周期性改鉴权算法**（表现为 `WSServerHandshakeError: 403`）。测试链路不该被一个
外部服务的改版卡死 —— 拿一段随便什么中文录音就能继续验证识别，这也是更真实的音源。

## 五之五、长期记忆（阶段 13）：MOSS 不再失忆

到阶段 12 为止，MOSS 的对话历史活在**内存里的一个 deque** 里：
程序一关就全没了，而且只记最近 3 轮。你上周告诉过它你叫什么，它不知道。

`memory.py` 把它换成**磁盘上的 JSON**，而且是两块分开存：

| | 存什么 | 窗口 | 为什么分开 |
|---|---|---|---|
| `dialog` | 最近 N 轮对话 | 滚动截断（默认 60 轮） | 是"流水"，太多要截 |
| `facts` | 长期事实（key-value） | 永久保留 | 是"沉淀"，多了才是价值 |

**分开是有道理的**：如果混在一起存，一截断就把事实也截没了 ——
"我上周告诉过你我叫什么"这种事，恰恰不能在几轮之后被冲掉。

```bash
# 日常使用：什么都不用加，记忆自动开
python moss_brain.py --auto --llm api --tts sapi --asr whisper

# 关掉（回到阶段 12 行为）
python moss_brain.py --no-memory ...

# 换个位置存（默认 pc_brain/data/moss_memory.json）
python moss_brain.py --memory-file D:/moss/my.json ...

# 喂给模型的对话轮数（默认跟 --asr-history 一致）
python moss_brain.py --memory-turns 5 ...
```

想看看它到底记住了什么 —— 就一个 JSON 文件，直接打开看：

```json
{
 "n_sessions": 2,
 "dialog": [["我叫张三", "好，我记下来了。"]],
 "facts": {"用户的名字": {"value": "张三", "at": 1791779047.9, "hits": 0}}
}
```

### 两个实现上的关键点

**1. 写盘必须原子。** 如果直接 `open(path,'w')` 再写，写到一半断电就留下半截文件，
下次启动解析失败 → **记忆全丢**。所以走"写临时文件 → `os.replace` 覆盖"：
同一分区内 rename 是原子的，要么旧内容、要么完整新内容，没有中间态。
真的读到坏文件时也不崩 —— 把坏文件改名叫 `.bad` 留档，然后从空记忆开始。

**2. "喂给模型几轮"和"磁盘上留几轮"是两回事。**
`--memory-turns` 只管"这次请求带几轮历史"（省 token），
`MemoryStore.max_dialog` 管"磁盘上保留几轮"（默认 60）。
把它们混成一个开关，就会出现"要么记不住、要么每句话都把 60 轮塞进提示词"。

### 事实验证：跨会话真的记得

实测跑两次（用同一个记忆文件，中间完全退出进程）：

```
第一次启动 → 对话 5 轮 · 长期事实 1 条
  [HEARD] 我叫张三
  [SAY] 好，我记下来了。        ← 调了 remember 工具

第二次启动 → 记忆文件……｜本次是第 2 次启动｜对话 5 轮｜长期事实 1 条
  （"用户的名字：张三" 出现在提示词的「你知道的关于用户的事」里）
结束 → 对话 8 轮 · 长期事实 1 条
```

## 五之六、工具调用（阶段 13）：MOSS 从"会聊"到"会办事"

阶段 12 之后 MOSS 能聊天了，但它只会**聊**：你问"几点了"，它只能编一个时间。

`moss_tools.py` 给模型一双手 —— 这就是 function calling（工具调用）。
流程是**两轮**：

```
① 模型看完提示词 → 返回 {"say": "", "tag": "", "tool": {"name": "get_time", "args": {}}}
                        ↑ 它先不说话，只"申请调用"
② 我们在本地真执行 → 把结果塞进第二条 user 消息再问一次
③ 模型拿到真实结果 → 返回最终 {"say": "现在是 2026年10月12日 星期一 12:23:37。", "tag": "time"}
```

### 为什么不用 OpenAI 的原生 tools 字段

1. **兼容性**：本项目的卖点之一是"任何 OpenAI 兼容接口都能用"。但 DeepSeek /
   通义 / 智谱 / 本地 ollama 对原生 function_calling 的支持程度差别很大。
2. **我们本来就要自定义格式**：每轮都得返回 `{"say","tag"}`（OLED 只认 ASCII），
   这已经是一个自定义协议了，再叠一层原生 tools 反而更乱。
3. **可控**：工具由**我们**执行。"能不能调、参数怎么清、超时怎么办"全在自己手里 ——
   对一个要连硬件的东西，这很重要。

### 第一版给了 7 个工具

| 工具 | 干什么 | 备注 |
|---|---|---|
| `get_time` | 查当前日期时间 | 本地时钟，永远可用 |
| `get_weather` | 查某城市天气 | 走 wttr.in，**免费、不要 Key** |
| `look` | 再看一眼画面（几个人、有没有动） | 读视觉线程的快照 |
| `remember` | 长期记住一件事 | 写进 `memory.py` |
| `recall` | 回忆记住的事 | 读 `memory.py` |
| `forget` | 忘掉某条 | 删 `memory.py` |
| `stats` | 查自己运行多久、听懂几句 | 自省 |

```bash
# 开工具（默认就开）
python moss_brain.py --auto --llm api --asr whisper

# 关掉
python moss_brain.py --no-tools ...

# 限制一个回合最多连调几次（默认 1，防死循环）
python moss_brain.py --tool-max-rounds 2 ...
```

单独测工具层（不需要网络、不需要硬件）：

```bash
python moss_tools.py
```

### 离线也有工具（关键词规则兜底）

`--llm offline` 时没有大模型来判断"该不该调工具"，但**规则也能覆盖大部分说法**，
而且比"编一个时间"好得多。`OfflineMind` 内置了这些模式：

| 你说 | 触发 |
|---|---|
| "现在几点了" / "今天几号" | `get_time` |
| "我叫张三" | `remember(用户的名字, 张三)` |
| "我是谁" / "你还记得我吗" | `recall` |
| "忘掉我喜欢安静" | `forget` |
| "深圳的天气怎么样" | `get_weather(深圳)` |
| "看看我" / "画面里有人吗" | `look` |
| "你是谁" / "你好" / "谢谢" | 直接回答（不调工具） |

### 踩坑记录（这个坑很典型）

**现象**：接上真 API 后，第一次调用就静默降级成模板台词，日志只有一行
`(api 失败兜底, 0ms)`，看不出原因。

**原因**：`TOOL_PROMPT` 里有一段 JSON 示例 `{"say": "", "tool": {...}}`，
而我们用 `TOOL_PROMPT.format(tools=...)` 注入工具清单 ——
**`str.format` 把 JSON 的花括号当成占位符了**，直接抛 `KeyError: '"say"'`。

**修法**：改用 `str.replace("{tools}", ...)` 注入，从根上避开转义问题
（只对 `{{}}` 做转义很容易漏掉一处）。

**教训**：这个 bug 只在"开了工具 + 走真 API"时才会出现 ——
只测离线规则、或只测不开工具的 API，都发现不了。
正是那个"假 LLM 服务端"的全链路测试把它逼了出来。

## 五之七、执行器（阶段 14）：MOSS 终于有"手"了

阶段 13 给它一双手，但那双手只会**查**和**记**。
它读得懂世界，动不了世界。

阶段 14 补上另一半：**模型能真的驱动硬件**。

| 工具 | 干什么 | 发出去的串口命令 |
|---|---|---|
| `set_led` | 灯环变指定颜色（支持"红/绿/蓝/青/紫/黄/橙/白/灭"，也可给 RGB） | `LED <r> <g> <b> [ms]` |
| `turn_motor` | 步进电机转 N 步（也说"转半圈/两圈"） | `SPIN <steps> CW\|CCW` |
| `beep` | 蜂鸣器响一声 | `BEEP <freq> <ms>` |
| `show_text` | 在 OLED 上写一行字（只认 ASCII） | `TEXT <text>` |
| `stop_all` | 急停：停电机、静音、灯环交还 | `STOP` |
| `device_status` | 问设备状态（发 PING 等 PONG） | `PING` |

```bash
# 接假设备（不需要真板子、不需要 Wokwi）
python tools/mock_esp32.py --port 4000                 # 终端 1
python moss_brain.py --demo --port socket://localhost:4000 \
    --llm api --api-base http://localhost:8000/v1 \
    --api-key fake --model mock-1                      # 终端 2
#   ↑ 注意 --port 是 socket:// 而不是 COMx ——
#     pyserial 天生支持 socket:// 伪 URL，所以假设备直接开 TCP 就行，
#     不用去折腾 Windows 虚拟串口。

# 单独测执行器层（不需要硬件）
python moss_actuators.py
python tools/mock_esp32.py --selftest
```

### 1. 核心设计：所有手动动作都**有时限**

状态动画是"自动挡"：`MODE` 一切，灯环就跟着状态呼吸/扫描。
手动命令是"人工挡"：整圈铺成指定颜色，**N 毫秒后自动归还**给状态动画。

为什么不永久锁住？因为 MOSS 是个"活的"东西。你让它变红一下，
它红完就该继续跟着状态呼吸；如果永久锁死，之后 `MODE` 切到 `SPEAK`
都不变色了 —— 那不是 MOSS，那是一台坏掉的路由器。

同理，`SPIN` 走完就断电（不让线圈干耗发热），`STOP` 是唯一的"立刻归还"。

### 2. 为什么单独一个模块，而不是塞进 `moss_tools.py`

执行器工具和查询类工具不一样：**没接设备时它们根本不该出现在清单里**。
让模型看到一堆 `set_led / turn_motor` 却每次都回"没接上设备"，
只会浪费 token 并把它带偏。

所以它们是**按需注册**的 —— `install(link)` 有设备才注册。

> ⚠️ 这一条必须用"**延迟注册**"实现，不能靠 `install()` 返回空表。
> 如果照常用 `@tool` 写在模块顶层，那么 `import moss_actuators`
> 这一下就已经把它们塞进注册表了，之后 `install()` 返不返回空表都没用。
> **这个坑真实踩到了**：`--no-actuators` 形同虚设、没串口也照样列出来，
> 而自检却是绿的（因为自检只验了 `install()` 的返回值）。
> 修法是把装饰器换成一张规格表，到 `install()` 里才真正注册；
> 自检里也补了一条"import 之后注册表里不该有执行器"的护栏。

### 3. 假设备为什么值得写

"发出去一条 `LED 255 0 0`"和"设备真的变红了"是两件事。
光看 PC 端日志，永远不知道指令有没有被设备**接受**、
参数有没有被**钳制**、未知命令有没有被**兜住**。

所以 `tools/mock_esp32.py` 按 `src/main.cpp` 里 `handleCommand()` 的
**同一套规则**解析，回**同样的那几行**：

- LED 值同样钳到 0..255、`ms` 同样有上限
- SPIN 同样 200000 步上限、方向大小写同样都认
- 未知命令同样回 help（而不是默默吞掉）
- 多一个固件没有的 `DUMP`：把内部状态吐出来，方便断言

### 4. 回真机 / Wokwi

固件侧新增了 `LED / SPIN / BEEP / STOP / PING` 五条命令（`src/main.cpp`），
HAL 层加了对应的"接管"接口（`hal_light.cpp` 的 `lightOverride/lightTick`、
`hal_motion.cpp` 的 `motionSpin/motionStop`、`hal_audio.cpp` 的 `audioSilence`）。

```bash
pio run           # 编译（RAM 6.1% / Flash 10.0%）
```

Wokwi 用 rfc2217 也是 **4000 端口**，和假设备冲突，二选一。

## 五之八、唤醒门（阶段 15）：什么时候**不用**答应

阶段 12 之后 MOSS 听得懂你说话，阶段 14 之后它能动手 —— 合起来就是：
**你说什么它都当真。**

你说"这段代码有 bug"，它可能真的去查一遍天气；旁边两个人聊天，
它插一句"我看见你了"；你打电话说"把空调关掉"，它去关灯。

唤醒词不是锦上添花，是一条**省钱和讲礼貌的分界线**。

### 1. 三条规则

| 你说了什么 | 结果 | 送进语言层的文字 |
|---|---|---|
| `MOSS，现在几点了` | 唤醒，**剥掉称呼** | `现在几点了` |
| `屏幕上写 MOSS` | 唤醒，**保留整句** | `屏幕上写 MOSS` |
| `MOSS`（只喊名字） | 唤醒，但**不当问题** | 空（只应一声"在"） |
| `这个 bug 在哪一行` | 拦下 | —— |
| 唤醒后 20 秒内再说任何话 | 放行（免唤醒） | 原句 |

为什么第 2 条不剥？因为"屏幕上写 MOSS"里 MOSS 是**宾语**，
抠掉就变成"屏幕上写"，语义反而错了。剥称呼只在**句首**做。

为什么要有窗口？没有它，你每问一句都得先喊一次名字，像在对着对讲机讲话。
窗口默认 20 秒，而且**每说一句滑动续期** —— 真正在连续对话时它一直醒着，
停下来 20 秒才睡。睡着时 OLED 上会写 `SAY MOSS`，免得你不知道要不要叫它。

### 2. 为什么是"文本后置门"，不是声学唤醒词

Porcupine / openWakeWord 那套声学唤醒词当然更省，但这里刻意没用，三个理由：

1. **要新依赖、常常还要 AccessKey** —— 而本项目一路坚持"零新依赖、离线可验证"。
2. **没有麦克风就完全验证不了** —— 而"先在没有硬件的情况下把逻辑跑对"正是本项目的策略。
3. **真正花钱的是大模型，不是识别**。本地 whisper 跑一句 0.3~1.5 秒、零成本；
   一次 LLM 请求才是真金白银。门开在识别之后，已经拦掉了绝大部分浪费。

将来要在真机上省到底，就在 `WakeGate` **前面**再串一个声学唤醒词 ——
接口（`feed → hit / ignore`）不用改。

### 3. 别名表，以及它的代价

真 whisper 在中文模式下几乎不会老实输出 `MOSS`，它可能给「莫斯 / 摩斯 / 莫司」。
所以有一张别名表。但**没有**做模糊音匹配，也刻意**去掉了「摩丝」** ——
因为它撞了常用词，而句首命中会剥称呼，
于是"摩丝发胶在哪买的"会被吃成"发胶在哪买的"（语义被改，比误唤醒更糟）。
这个坑是自检里抓出来的。

代价是**已知的假阳性**：`摩斯密码怎么用` 会被当成喊名字。
这是刻意接受的取舍 —— 宁可偶尔多回一句，也不要你喊三遍没反应。

### 4. 用法

```bash
# 默认：开 --asr 就自动开唤醒门（说"MOSS"才理你）
python moss_brain.py --llm api --api-base ... --asr whisper

# 关掉，回到阶段 14 行为（任何人说话都回应）
python moss_brain.py ... --no-wake

# 自定义唤醒词（逗号分隔可以给多个）
python moss_brain.py ... --wake-word "小智,小知"

# 只认句首（怕闲聊时被误唤醒）
python moss_brain.py ... --wake-strict

# 窗口调长/调短
python moss_brain.py ... --wake-window 60

# 叫醒时让设备"嘀"一声（蜂鸣不占语音通道，比说话礼貌）
python moss_brain.py ... --wake-ack beep
```

`--asr-test` 会自动绕过唤醒门 —— 它的职责是量"识别准不准"，
被门拦掉就永远等不到结果了。

**拍手不受影响**：拍手走的是独立的事件通道，不经过这道门。

### 5. 怎么验证

```bash
python wake.py      # 不需要麦克风，纯文本，30 来个用例
```

再配一个"混着说话的"端到端：假 ASR 的脚本里故意塞进无关句子，
看它们是不是真的被安静放过：

```bash
python tools/mock_llm_server.py --port 8000 --once 90 &
python tools/mock_asr_server.py --port 8010 \
    --script "MOSS 现在几点了|这个 bug 在哪一行|MOSS 转半圈" &
python moss_brain.py --demo --no-window --wake-window 0 \
    --asr api --asr-api-base http://localhost:8010/v1 --asr-api-key fake \
    --llm api --api-base http://localhost:8000/v1 --api-key fake --model mock-1
```

`--wake-window 0` 是为了让每一句都必须喊名字 —— 默认的 20 秒窗口下，
除了第一句以外全都"免唤醒"，就验不出过滤了。

## 五之九、主动行为（阶段 16）：它自己也会动

到阶段 15，MOSS 的交互是**完美对称**的：你叫它，它答；你不叫，它就是个摆件。

但 550W 不是摆件。它会先看你一眼，再决定要不要说话。

### 1. 这一层的真正难题不是"怎么动"

把"看到人脸就转头"写成代码只要三行。难的是**它不该每次都转**：

- 你坐在它面前两小时，它不该转 7200 次
- 你正跟它说话，它不该突然"咔"一声转个圈给你看
- 你刚让它安静，它不该拿蜂鸣器跟你打招呼
- 总共就一个电机，不能同时转头和急停

所以 `behave.py` 里大部分代码是**约束**，不是动作：

| 约束 | 防的是什么 |
|------|-----------|
| 边沿触发（0→1 / 1→0） | 脸一直在，不该每帧都动（20Hz × 2 小时 = 14 万次） |
| 每行为独立冷却 | 一分钟里来来回回十次，不该动十次 |
| 全局节流（默认 6s） | 转头和闪灯不该叠在一起，看起来像抽风 |
| 权限分级 | 万一日志/逻辑出岔子，最坏情况也只是"转个头" |
| 说话时降级 | 出声的动作会和它自己的嗓子抢，也盖不住你说的话 |

### 2. 权限分级：为什么按"会不会发出声音"切

分界线刻意选在**声音**上，而不是"动作大小"：

- **L0（默认）**：转头、改灯环颜色。**不发出声音、不打断任何人**，
  最坏情况就是"转了一下"，你顶多觉得它有点活泼。
- **L1**：加上蜂鸣器。蜂鸣会打断你的思路、会在夜里吵醒人 ——
  所以需要你明确点头。

注意 L0 里**没有** `stop_all`、没有写屏幕、没有长时间占据电机。
不是不能做，而是"主动做"这件事本身要克制：
**它自己决定要做的事，应当是撤销成本为零的事。**
真正会改变世界的动作（停机、独占机构）永远该由你开口。

两条礼仪是**自动**的，不用配置：

```python
if 它在说话:  权限降到 L0   # 不拿蜂鸣盖住自己的嗓子
if 你在说话:  权限降到 L0   # 不抢戏
```

### 3. 和"模型调工具"的分工

阶段 14 的执行器工具是**模型**在调 —— 那是"你说，它做"，
要走一次网络往返，一秒多。
这里是**本地反射**在调 —— 不走网络、不走大模型，20Hz 的循环里直接判。

为什么不全交给模型：**"有人来了转个头"应该是立刻的**。
等你问完大模型，人已经走了。

### 4. 用法

```bash
# 默认 L0：有人来转头 + 变蓝灯，人走转回来 + 暖橙
python moss_brain.py --port COM5 --llm api ...

# 允许它"打招呼"（加蜂鸣）
python moss_brain.py --port COM5 --autonomy l1 ...

# 完全被动，回到阶段 15 行为
python moss_brain.py --port COM5 --no-proactive ...

# 节流放宽/收紧
python moss_brain.py --port COM5 --proactive-gap 15 ...
```

没接设备时这一层**自动关闭** —— 主动行为的产物就是"往设备发命令"，
没设备它只是个空转的状态机。

### 5. 怎么验证（这里有个坑）

`--demo` 的合成场景里 **`faces` 永远是 0**（Haar 认不出画出来的圆，
见 `DemoScene` 的注释）。所以"有人来了转头""人走了转回来"
这两条**最核心**的主动行为，在 demo 模式下一次也走不到。

要么架真摄像头，要么把"人脸"这一步换成脚本：

```bash
python behave.py                  # 引擎全部逻辑（假时钟，不依赖真实时间）
python tools/behave_e2e.py        # 人脸序列 → 引擎 → 真串口 → 假设备
python tools/behave_e2e.py --autonomy l0   # 顺带验证 l0 不会发出 BEEP
```

`behave_e2e.py` 保留**真的**引擎、**真的**串口协议、**真的**设备解析，
只把"摄像头看到几张脸"换成一段写死的序列。它断言的是
**假设备原样回了什么**，而不是我们自己拼的命令 —— 这样连"固件端解析对不对"
一起验了：

```
[SPIN] 1024 steps CW      ← 看见人，转头
[LED] 0 80 255 hold 2500ms
[BEEP] 1500Hz 60ms        ← 只有 l1 会有这条
[SPIN] 1024 steps CCW     ← 人走了，转回来
[LED] 255 120 0 hold 800ms
```

## 五之十、全双工（阶段 17）：它说话的时候，你也能插嘴

### 1. 阶段 17 之前它是个"半个聋子"

阶段 11 解决了一个很危险的问题：**自说自听**。

音箱放出去的声音会被自己的麦克风听见 → 融合逻辑以为"有人在讲话" →
进 `SPEAK` → 又说一句 → 又听见……**正反馈**，MOSS 会自己跟自己聊起来，
而且能聊到天荒地老。当时的解法很直接：**说话期间把听觉按静音算**
（`gated`），也就是"**半双工**"。

这个解法没问题，但代价是：

> **它一开口，你就插不上话了。**
> 想说"等一下"、"不对，我问的是……"，它一个字都听不见，
> 只能等它把这句台词念完。而它的台词有时候挺长的。

这就是阶段 17 要修的东西。

### 2. 正确解法：把"自己的声音"从麦克风里减掉

问题的根源不是"麦克风听见了扬声器"—— 那是物理必然，躲不掉。
根源是**听见了却分不清是不是自己**。

那就别分：**我本来就知道自己刚才放了什么**。
把那串波形从麦克风信号里减掉，剩下的就是"房间里的别人"。

这就是 **AEC（Acoustic Echo Cancellation，回声消除）**，
手机免提、视频会议用的都是它。

```
远端（我要念的台词）────────────┐
                                │  ← 参考信号（ReferenceBuffer）
                                ▼
麦克风 ──► [自适应滤波器 ĥ] ──► 减 ──► 残差 e ──┬──► 还要不要压？（残余抑制）
   │                            ▲                │
   └── 混着：回声 + 用户说话 ────┘                └──► 送去分段/识别
                    （+房间混响、本底噪声）
```

🔑 **整件事的关键是"参考信号"**：必须先知道"扬声器此刻在放什么波形"，
才谈得上减。所以 `voice.py` 那一层做了改动 —— 每念一句之前，
把**即将播出的 PCM** 登记进 `ReferenceBuffer`，同时带上时间戳。

真机上的两个硬骨头，以及这里是怎么处理的：

| 难题 | 做法 |
|---|---|
| **时间对齐**：放出去的和录进来的差多少？声卡驱动、蓝牙、USB 各不相同，几十到几百毫秒。 | 不猜。滤波器有 252ms 长，那点固定延迟被它**当成时延吸收掉**。另外只暴露"**已经播出去的**"样本（未来的填 0），参考缓冲自带时间轴。 |
| **双讲**：你和它同时在说的时候，滤波器会把自己的声音也当成回声去学，然后发散。 | 检测到"麦克风比回声估计大好几倍"就**冻结更新**（DTD），并且**不施加**残余抑制 —— 那正是你在说话的时候。 |

### 3. 三道闸，和一个必须一致的地方

音频进来之后要过三道关，任何一道不对，全双工就白做：

```
麦克风块
   │
   ├─①【AEC】减掉回声 ──────────────────────────► aec.py
   │
   ├─②【分段器闸】"现在是不是只有我自己的声音？"
   │       是 → 不往识别里送（旧半双工；现在改成"标成没人说话"）
   │
   └─③【融合层闸】状态机要不要把这块当"有人在说话"
```

②和③**必须用同一个判据**，否则会出现这种诡异症状：
分段器放行了、识别也认出来了，但融合层还按静音算 ——
屏幕上永远挂着 `SPEAK`，你喊它它也纹丝不动。

所以判据只写一份，是个模块级函数：

```python
# moss_brain.py
def echo_blind(speak_worker, aec, refbuf):
    """现在是不是「MOSS 在说话，而我不知道它在放什么」"""
    if speak_worker is None or not speak_worker.busy():
        return False
    if aec is not None and refbuf is not None and refbuf.active:
        return False       # 有参考 → 交给 AEC，麦克风保持打开 → 真·全双工
    return True            # 没有参考 → 退回老办法，说话期间屏蔽听觉
```

⚠️ 注意它问的是 **"此刻缓冲里到底有没有东西"**，而不是 **"--aec 开没开"**。
因为开了也可能拿不到参考：SAPI 合成到文件失败、mp3 解码失败、临时文件写不进去。
那种情况下如果还傻开着麦克风，MOSS 立刻退化成"自己跟自己聊"。
所以**拿不到参考就不是全双工，只是退化回半双工** —— 功能不丢，也不会翻车。

### 4. 用法

```bash
# 默认就开（auto：有嗓子、且这个嗓子给得出参考信号，才开）
python moss_brain.py --tts sapi --asr whisper --llm api ...

# 关掉（戴耳机时其实没必要开，见下）
python moss_brain.py --aec off --tts sapi ...

# 蓝牙音箱 / 高时延设备：滤波器加长
python moss_brain.py --aec-taps-ms 400 --tts sapi ...

# 还是能听见自己的回声 → 双讲门调紧一点
python moss_brain.py --aec-dtd 1.5 --tts sapi ...
```

启动横幅里会明确写出它的状态：

```
全双工：频域分块 PBFDAF（63 分块 × 128 点 FFT） · 4032 抽头(252ms) · 步长 0.50 · 双讲门 2.0× · 残余抑制 10dB
全双工：关闭（--demo 是合成音频，没有真实回声回路；--aec on 可强制开）
全双工：关闭（这个嗓子给不出参考信号，用 --aec on 可强制开）
```

### 5. 什么时候**不需要**它

**戴耳机**的时候。

耳机的声音不出现在房间里，麦克风根本听不到 —— 压根没有回声可消。
这时候正确的做法是 `--aec off --no-echo-guard`：关掉 AEC，
也关掉"说话时屏蔽听觉"那道闸。你会得到**没有延迟、没有残留**的真全双工，
比任何 AEC 都干净。

AEC 是给**扬声器外放**准备的（笔记本内置喇叭、蓝牙音箱）。
先用 `tools/aec_live.py` 量一下你这套设备到底有没有回声（见下）。

### 6. 怎么验证

任务的关键不是"减掉多少分贝"，而是"**我插嘴它到底听不听得见**"。

```bash
python aec.py --selftest               # 7 组，合成房间里的滤波器行为
python tools/fullduplex_e2e.py         # ★ 四个场景的端到端（出声前不需要麦克风）
python tools/aec_live.py               # 只静默录音，量本机噪声底（不出声）
python tools/aec_live.py --yes         # 真放声音，量你**这台机器**的回声与时延
```

`fullduplex_e2e.py` 是阶段 17 的核心验收。它保留**真的**分段器、
**真的**识别线程、**真的** `AudioWorker`、**真的** `echo_blind()`，
只把两样东西换成仿真：麦克风用假房间把回声灌回来、嗓子只在参考缓冲上登记。
然后跑 2×2 四个场景：

| 场景 | 配置 | 期待 | 说明 |
|---|---|---|---|
| **S1** | AEC 开 · 有人插话 | 切出一句，且判成"**用户**" | 真·全双工 ✅ |
| **S2** | AEC 关 · 有人插话 | **一句都切不出来** | 旧半双工：插话被整个吞掉 |
| **S3** | AEC 关 · 没人插话 · 不设闸 | 切出一句，判成"**自己**" | 反面教材：不设闸就自问自答 |
| **S4** | AEC 开 · 没人插话 | **一句都切不出来** | 回声清干净了，不自说自听 |

S1 和 S2 的对比 = 阶段 17 到底解决了什么；S3 和 S4 的对比 = 为什么不能"干脆别屏蔽麦克风"。

它怎么判"这句话是用户的还是自己的"：让两个嗓音基频明显不同
（205Hz vs 118Hz），识别引擎用一个频带能量比来分。开跑前会先在**纯信号**上
把这个判据标定一遍，数字打出来，分离不好当场看得见：

```
判据标定（纯信号，不含回声/噪声）：
  MOSS 的嗓子（f0=118Hz） 比值 = 0.264   → 判「自己」✓
  用户的嗓子（f0=205Hz） 比值 = 0.997   → 判「用户」✓
  分离度 = 0.733（阈值 0.55，越大越稳）
```

### 7. 这一步踩过的坑（都是真的，记在这儿免得下次再踩）

1. **NLMS 的分母少乘了块长** —— 有效步长直接大 63 倍，滤波器瞬间发散。
2. **时域收敛太慢**：语音的频谱很不平（低频比高频高十几个 dB），
   单一全局步长被低频绑死。改用**频域逐 bin 归一化**（PBFDAF）后，6 秒的 ERLE 从 1.8dB 提到 13.8dB。
3. **频域有四种写法的组合**（误差放前半段还是后半段 × 取不取共轭），
   实测只有一种收敛，另外三种是发散的。写成注释钉在代码里了。
4. **双讲判据自指**：判"该不该用这条判据"的量，本身要靠这条判据放行才能估出来 ——
   冷启动永远冻结。跟 `asr.py` 里"用 dbfs 还是 listening"是同一类坑。
5. **双讲误报**（这条最隐蔽）：判据的门槛用"回声估计占参考的 5%"就算收敛，
   结果把**收敛过程中间**那一大段直接放行 → 滤波器学到一半被反复冻住 →
   残差一直很高 → 下游把残差当成"用户在说话"。
   **MOSS 开始自己回答自己。** 是 `fullduplex_e2e.py` 的 S4 场景翻车才发现的。
   修法：另找一个**跟"有没有人"无关**的量来判收敛（残差/麦克风），
   而且要**持续**低于门槛才算（用 EMA，不是取最小值）。
6. **混响尾巴**：扬声器一停，参考缓冲立刻变成**精确的零**，
   但房间里的声音还会响 100~200ms。实测播放在 3.00s 结束，
   3.04/3.11/3.17s 的麦克风里还躺着 -31/-27/-37dBFS 的尾巴。
   于是"只有回声"那道闸在最需要它的时候关掉了，尾巴被当成用户。
   修法：把"**此刻在放**"和"**余音还在**"拆成两个概念，
   余音期内照样按"有回声"对待。
7. **测试的盲区**：原先的双讲测试只断言"插话那 25 块**检出了**多少"，
   而对**没人插话时误报了多少**一个字都没说 —— 上面的 bug 恰好全在盲区里。
   已在 `aec.py` 里补了两条断言（误报率 ≤10%、残留回声压在 VAD 门限之下）。
8. **"时间轴跳变"门槛定得比声卡抖动还小**（**真机才暴露，仿真永远测不出来**）：
   判跳变用的是 `子块长 × 3` = **12ms**，理由是"块内每步严格 4ms"。
   块内确实严格，但**跨块**那一步不是 —— 块的时间戳来自声卡回调
   （`time.time()`），实测在 **-1ms ~ +14ms** 之间乱跳（MME 尤其明显）。
   于是正常抖动就把门槛打穿，实测 47 帧里报了 20 次"跳变"。
   后果**不是崩溃，是悄悄变差**：每报一次就把参考历史清空，滤波器刚学到的
   回声被抹掉，收敛反复从头开始。第一版修法是把门槛放宽到 30ms（治标）。
9. **真正的病根：把抖动的时间戳当成了时间轴**（第 8 条的治本修法，见第 9 节）：
   上一条放宽门槛只是让它别误报。可 `t_end` 不只用来判跳变，它还要
   `ref.window(t_end, ...)` **取参考样本** —— 时间戳抖 ±8ms，取到的参考
   就整体错位 ±128 个样本，参考和麦克风直接去相关。这一条是在自检里
   加了一组「时间戳抖动」用例才量出来的：**ERLE 从 23.2dB 掉到 8.1dB**。
   正解不是继续调门槛，而是**别再拿时间戳当时间轴** —— 自己按样本数走
   （详见第 9 节）。改完抖动下 ERLE 回到 23.2dB，和精确时钟一模一样。

### 9. 时间轴：自己养一条时钟（坑 8/9 的治本修法）

这一节记的是**整个阶段 17 里最值得留下的一段**，因为它同时说明了
"仿真测不出什么"和"一个量被用在两个地方有多危险"。

**问题的形状**：`process()` 拿到一个麦克风块和一个时间戳 `t_end`，
`t_end` 被用在两个地方 ——

1. 判"时间轴有没有跳变"（丢块 / 卡顿 / 换设备）；
2. `ref.window(t_end, ...)` —— **取这一段对应的参考样本**。

第 2 条对精度的要求是**一个样本**（16kHz 下 62.5µs）。而 `t_end` 来自声卡回调的
`time.time()`，实测抖动 **±10ms**，比要求高两个数量级。抖 8ms = 错位 128 个样本，
参考和麦克风就此去相关 —— 滤波器再强也对不上一个随机乱跳的参考。

**两条认清楚之后才行**：

- **抖的只是时间戳，音频本身是连续的。** 声卡每块交上来 n 个样本，
  它们的间隔严格等于 `1/sr`，一分不差；抖的是"回调什么时候被执行"。
- **整体差一个常数完全无所谓。** 回放 → 采集之间本来就有几十毫秒的固定延迟
  （驱动缓冲 + 空气 + 采集缓冲），它从头到尾不变，直接落进滤波器的
  第一个抽头里被吸收掉。我们要的只是它**不变**，不是它等于几 ——
  这正是 [5/7] 那组测试（12/55/90/130ms 四档时延、一行参数都不用给）验的东西。

**所以做法**：锚定一次之后，按**样本数**推进一条内部时钟，不再理后面每一块的
时间戳；时间戳只留着"对表"：

```python
if self._last_t is None:
    t_use = t_end                     # 第一次：先认声卡的时间戳
else:
    pred = self._last_t + dur         # 内部时钟：上一块末尾 + 这一块时长
    if abs(t_end - pred) > self.gap_tol:
        self._drop_history()          # 真跳了 → 参考历史作废、重新对表
        self.n_gap += 1
        t_use = t_end
    else:
        t_use = pred                  # 正常：不信这次的时间戳，按样本数走
```

**带回三个好处**，都是白拿的：

| 好处 | 原因 |
|---|---|
| 抖动彻底不影响参考对齐 | 时间戳根本不参与取样 |
| 判跳变从"跟抖动比大小"变成"跟噪音比大小" | 跨块那一步从 `4ms ± 10ms` 变成严格 4ms |
| 丢块变得**可测** | 内部时钟预测 vs 实际时间戳，跳一个块就是 64ms，一眼分得开 |

**但必须成对地测**（这一条是刻意的）：给第 6 组自检加了**反向**断言 ——
造一次真丢块（音频和时间戳**一起**往前跳一个块），断言 `n_gap == 1`。
少了这条，将来有人为了让抖动用例过关，把门槛一路放宽甚至删掉判跳变，
丢块就会漏过：那时参考历史里存的是错位的参考，**比不复位还糟**。
判据有了"该响的时候响"，还必须配上"不该响的时候别响"，反过来也一样。

## 五之十一、强视觉（阶段 18）：它终于"看得见东西"了

### 1. 阶段 18 之前，它其实"看不清"

阶段 9 的视觉层只有两样本事：**Haar 人脸检测** + **帧差运动检测**。
这直接决定了两件事：

| 症状 | 根因 |
|---|---|
| 问"帮我看看画面里有什么"，它只能答"有 1 个人，没在动" | 视觉层**从来没看出来过别的东西** —— 不是 `look` 偷懒 |
| `--demo` 下 `faces` **永远是 0**，阶段 16 的主动行为在合成场景里根本测不到 | 合成场景画的是小圆球，**没有脸**，Haar 当然找不到 |

第二条一直是个隐患：一个功能"只能靠专用探针才测得到"，平时就没人会去碰它。

阶段 18 要做的就是**把眼睛换掉**：Haar → `yolov8n`（COCO 80 类）。

### 2. 为什么是 ONNX + onnxruntime，不是 ultralytics

```
python vision.py --image tools/assets/desk_objects.png
→ cup 0.91 · keyboard 0.84 · bottle 0.82
```

要跑 YOLO，最顺手的写法是 `pip install ultralytics` + `model = YOLO("yolov8n.pt")`，
一行就完事。**没这么干，理由是依赖体积**：

| 方案 | 要多装什么 | 体积 |
|---|---|---|
| ultralytics | 顺带拖进 **PyTorch** | **2 GB+** |
| **onnxruntime** | **什么都不用装** | 0 |

关键是 `onnxruntime` **本来就在** —— 阶段 12 的 `faster-whisper` 依赖它，
早就装好了。于是只要拿到一个 `.onnx` 文件，推理这件事就完全免费。
（同理，NMS 用的是 OpenCV 自带的 `cv2.dnn.NMSBoxes`，不需要 `torchvision`。）

**模型文件不走 pip，走 hf-mirror.com** —— 和阶段 12 下 whisper 模型是同一个理由：
本机连不上 GitHub（实测超时），而 hf-mirror 980 ms 就响应。12 769 720 字节，
下完 3.4 秒。下载函数**先写 `.part` 再 `os.replace`**，所以下到一半断网
不会留下一个"看起来存在但其实是坏的"模型文件 —— 那种文件最难查。

### 3. 检测器接口：为什么里面**必须**有一个 `fake`

`vision.py` 里所有检测器都实现同一个接口，共五档：

| 后端 | 说明 |
|---|---|
| `auto` | 按 yolo → haar 顺序探测，用哪个看环境 |
| `yolo` | 真目标检测（ONNX） |
| `haar` | 阶段 9 的老眼睛，只有人脸 |
| `null` | 彻底关掉视觉检测 |
| `fake` | **按剧本产框，不读画面** |

`fake` **不是玩具，是必需品**。理由和 `behave_e2e.py` 造假人脸、
`mock_esp32.py` 假设备、`_FakeVoice` 假嗓子完全一样：

> **目标检测本身是有噪声的** —— 换个模型、差一点光照、调一下阈值，
> 框就会闪。拿这种会闪的东西去验证**下游**逻辑（`fuse()` 的规则、
> `look` 的措辞、`BehaviorEngine` 的触发），等于在沙子上盖楼：
> 测试红了，你分不清是下游写错了，还是这一帧恰好没检出。

`fake` 把"检测"这一步变成**确定的剧本**：第几帧该出什么框、叫什么名字、
多大置信度，全部写死。下游逻辑于是有了确定的输入。

顺带解决了一个老问题：`--vision-model fake` 能给合成场景**造出人脸**
（`faces` 从恒为 0 变成 1），阶段 16 的主动行为终于能在 `--demo` 下直接测了。

### 4. 降级链：`make_detector()` 永远不抛异常

```python
detector = make_detector("auto", mdir, mirror, **kw)
# 拿到的一定是个能用的检测器，外加一句 note 说明"实际用的哪个、为什么"
```

| 请求 | 结果 |
|---|---|
| 要 yolo，模型在 | yolo |
| 要 yolo，模型不在 / onnxruntime 没装 | **降级 haar**，`note` 写明原因 |
| 要 yolo，连 haar 的 xml 都没有 | **降级 null**，`note` 写明原因 |

这是**故意的**：视觉是"锦上添花"，听觉和对话是"主干"。
模型没下好让整个 MOSS 起不来，是最糟糕的失败方式 ——
用户以为程序坏了，其实只是少了个可选文件。

### 5. 两种检测，两种速率（这是个容易忽略的设计点）

摄像头 30 fps，但两件事的代价差 10 倍：

| 做什么 | 耗时 | 频率 | 为什么 |
|---|---|---|---|
| 运动检测 | ~6 ms | **每一帧** | 手抖一下就是一两帧的事，隔帧采样就漏了 |
| 目标检测 | ~50 ms | **每 3 帧一次**（`--vision-detect-every`） | "桌上有几个杯子"每 0.2 秒问一次，和人眼分辨不出区别 |

**ONNX 的线程数被刻意压到 2（不是"用满所有核"）**。因为 AEC 要求 64 ms
一块**不能滑**：视觉掉到 15 fps 一点损失都没有，可丢一块音频就是漏半句话。
让视觉线程去抢满 CPU，亏的正好是最不能亏的那一头。

### 6. 说人话：量词、"等 N 样东西"、以及别说两遍

检测出来的是框，人听的是一句话，中间这段要写对：

```
1 个书          ✗        1 本书          ✓      ← 量词例外表 COCO_MEASURE
1 个杯子、1 个键盘、1 个瓶子、等 5 样东西  ✗      ← "等"被读成了第 4 样东西
1 个杯子、1 个键盘、1 个瓶子等 5 样东西    ✓
```

量词表里没有的类一律用"个"，**不猜** —— 猜错（比如"1 条键盘"）比用"个"难看得多。

`look` 工具那条也有个细节：**"人"只能说一遍**。第一版按"用的哪个后端"来判断
要不要补一句"画面里有 N 个人"，结果 YOLO 模式下 `1 个人` 被说了两遍 ——
因为物体列表里本来就有 `person`。改成按**"人是不是已经在上面那句话里说过了"**
判断，逻辑才和实际输出对上。

### 7. 怎么验证

```bash
# ① 视觉层自检（7 组，不需要摄像头、不需要模型）
python vision.py --selftest

# ② 端到端探针（A 离线链 / B 真模型 / C 整条链）
python tools/vision_e2e.py
```

自检 7 组分别是：letterbox 几何可逆 · 通道顺序真翻了 · 后处理（含**两种坐标约定**）·
NMS（重复压掉、跨类不压）· COCO 类表 · 说人话的措辞和折叠 · 假检测器剧本。

探针分三段，**A 段完全不碰模型和摄像头**，所以 CI 里也能跑：

| 段 | 测什么 | 依赖 |
|---|---|---|
| A1–A7 | 空场景→IDLE、有人→VISION、有人+杯子→带物体名、只有运动→`moving + cup`、检测器每帧炸→视觉线程活着、检测器关→`look` 说实话、`detect_every` 真的在抽帧 | 无 |
| B | 两张**真照片**喂给**真 yolov8n**，两种分辨率各验一遍标签和"框不出画面" | 模型 |
| C | 真照片 → 真检测 → 真 `fuse()` → 真 `look()`，整条链一次走完 | 模型 |

B 段那句"**没有一个框跑出画面**"是刻意加的断言 —— 它专抓"逆 letterbox 算错"：
坐标换算错了框会整体偏移，而偏移最容易的表现就是跑出边界。只验"检出了什么"
是抓不到这种错的。

> 照片是**真照片**（`tools/assets/`），不是合成色块。合成色块证明不了检测器好使 ——
> 它只能证明"代码把某个张量解成了某个数"。

### 8. 这一步踩过的坑（都是真的）

1. **坐标约定搞错，冤枉了模型半天**（最坑的一个）：
   Ultralytics 自己导出的 ONNX 给**像素**坐标（0~640），
   可本机默认下的这个第三方导出给的是**归一化**坐标（0~1）。
   把归一化当像素用 → 框全挤在左上角；更糟的是配合"丢掉退化框"
   （`w > 1.0` 才算有效）→ **所有框都被当成碎片扔掉** → 表现成"什么都没检测到"。
   第一反应是"这模型不行"，其实是解码规矩搞错了。
   修法：`_coord_convention()` 自动判（拿四个坐标的最大值看 ≤2 还是 >2），
   再把退化框过滤**挪到坐标换算之后** —— 顺序错了照样全丢。
2. **`to_blob` 要同时做两件事：BGR→RGB **和** HWC→CHW**。
   两件都错会**互相抵消** —— 于是它在某一张图上"能跑"，
   换一张就明显不对。这种错最难查，因为它会给你一个"有时对"的假象。
3. **同数量的次级排序写了两份实现**：日志里的 `objs`（走 `labels_line`）
   按**中文名**排，OLED 上的短标签（走 `count_objs`）按**英文名**排。
   `cup`/`laptop` 两种排法恰好同序，一直看不出来；
   直到 `keyboard`(键盘) 和 `laptop`(笔记本电脑) 撞上 ——
   同一条日志里写 `laptop` 在前、OLED 写 `keyboard` 在前，自相矛盾。
   不报错、不影响功能，只是让人对着两份输出反复怀疑自己看错了。
   修法：`count_objs` 直接委托给 `vision.count_by_name`，只把三元组削成二元组。
4. **探针夹具写死了 `"detector": "fake"`** → "检测器关掉"那个用例
   照样报"没认出什么东西"，测了个寂寞。**夹具造假，测出来的结论就是假的。**
5. **探针 A4 偶发红（3 次里红 1 次）**，查了两轮：
   第一轮是拿演示场景当夹具，忘了它有一段是**静止**的；
   换成专用运动场景后又红 —— 因为 `sin()` 在峰值附近**每帧位移不到 1 像素**，
   运动量掉到阈值以下。最后换成**恒定每帧 18 像素**的步进，运动量稳定在
   0.0466（阈值的 5.8 倍），连跑 5 次全绿。
   **测试要么稳定地过、要么稳定地不过；"偶尔红"最消耗人。**
   （两轮是同一个毛病的不同变体：第一次是"忘了它有一段静止"，
   第二次是"以为平滑就是均匀"。）
6. **`1 个书`**、以及 `…、等 5 样东西` 里那个多余的顿号 —— 见第 6 节。

### 9. 性能（本机实测）

| 项 | 数字 |
|---|---|
| 模型大小 | 12.2 MB（`yolov8n.onnx`，COCO 80 类） |
| 纯推理 | ~36 ms/帧（CPU，2 线程，640×640） |
| 整条 `detect()`（读图+缩放+NMS） | **50~70 ms/帧** |
| 主循环实测 | 400 次融合 → 视觉 599 帧、**跑检测 200 次**（每 3 帧一次）— 和 `detect_every=3` 对得上 |

**为什么"纯推理 36 ms"和"整条 detect 50~70 ms"要分开写**：
差的那部分不是模型慢，是前后处理（解码、letterbox 缩放、NMS）。
不分开写，下次有人发现"怎么变慢了"，会去怀疑模型和线程数，
而真正的问题在前后处理里。

## 五之十二、变化感知（阶段 19）：它自己注意到桌上多了个杯子

新增文件：`presence.py`（滤波层），改 `behave.py`（物体事件 + 权限分级 + 说话）。

### 1. 阶段 19 之前，它只会"一问一答"

阶段 18 给了它一双能认东西的眼睛，但用法很被动：

```
你：帮我看看画面里有什么
它：我看到 1 个杯子、1 个键盘
```

你不问，它就永远不吭声。桌上多了个杯子、你把键盘挪走了 —— 它都不知道。
阶段 19 补上这一半：

```
（你放下一个杯子，没说任何话）
它：我注意到画面里多了 1 个杯子。
```

**和 `look` 工具的分工**：`look` 是"你问它就答"，走大模型；
这里是"它自己决定要不要开口"，走本地反射（和阶段 16 的"有人来了转个头"同一条路）。
两条路共用同一层节制（节流、冷却、权限）—— 各起一套的话，
"转头的冷却"和"说话的冷却"会各算各的，两条叠起来就是抽风。

### 2. 难点不是"看得出变化"，而是"别把抖动当成变化"

人脸的出现/消失是**干净**的：一张脸在不在，逐帧看基本一致。
所以阶段 9 那套代码可以放心写成"上一帧没有、这一帧有 → 有人来了"。

**物体检测不是这样。** 同一个杯子，yolov8n 可能给：

```
第 1 帧 0.91 → 第 2 帧 没有（被手挡了一下）→ 第 3 帧 0.89 → 第 4 帧 没有
```

个数还会在 1 和 2 之间跳（重叠框、或者杯子被挡掉一半）。
直接按"这一帧有没有 cup"判断，结果就是 MOSS 变成坏掉的报警器：

```
多了个杯子、杯子没了、多了个杯子、杯子没了、多了个杯子……
```

所以 `presence.py` 里大部分代码是**滤波器**，不是识别器。
这和阶段 16 是同一个道理：**难点不在"会不会动"，而在"什么时候别动"。**
这里是：难点不在"能不能看出变化"，而在"**别把噪声当成变化**"。

三道滤波：

| 滤波 | 做什么 | 为什么 |
|---|---|---|
| **迟滞** | 每个类一个分数，检出 +1、漏检 −1，封在 0..9。分数 ≥3 算在场，掉回 0 才算不在场 | 于是"来"要连续攒够 3 次检出，"走"要连续掉够 7 次漏检。**一帧漏检只是退一格、不归零**，所以"检出/漏/检出/检出/漏"也攒得够 —— 真实检测本来就是这么抖的 |
| **个数确认** | 个数变了要连续 3 次看到同一个新数字才认账 | 个数是**二阶**信息，比"在不在"更容易被噪声影响（两个框重叠一下就变成 2 个） |
| **暖机** | 头 10 次检测只养状态、不产生变化 | 一开机画面里本来就有桌子、键盘、显示器。把它们当"新增"，它一启动就报一屋子 —— 那是噪音，不是观察 |

**三个不对称，每一个都是刻意的：**

- **离开（7 次）比进入（3 次）钝得多。** 不是性能问题，是**两类错误的代价不一样**：
  晚一点发现"东西没了"只是反应慢，0.7 秒后补上就完了；
  把"暂时没看见"说成"没了"，那是**编造事实** —— 而它说的话是要被当成真的听的
  （还会调工具、记事情）。**宁可迟钝，不许撒谎。**
- **命中率只有一半的目标宁可不认。** 自检里有一条断言专门盯着这个边界：
  `[杯子, 空] × 20` 严格交替 → `visible()` 必须是空的。
  写这条是为了防止将来有人为了让"抖动的杯子"那条过，把门槛一路调低，
  最后把噪声也认进来。（判据要**两个方向都测**，这个项目反复踩过。）
- **确认"在场"的那一刻，分数直接顶到上限。** 少了这一步，刚够 3 分就被漏检往回啃，
  漏 3 次就掉出去了 —— "离开要 7 次"**从来没生效过**，两个门槛互相削弱、等于只剩一个。
  这个 bug 是自检第一次跑就抓到的。

关于门槛单位还有一句必须说的：**它的单位是"检测次数"，不是"帧"**。
所以 `PresenceTracker.update()` 只在**检测那一次**调用，不是每帧调。
每帧调一次等于偷偷把"连续 3 次检出"变成"连续 1 次"，而且
`--vision-detect-every` 一改、行为就跟着变 —— 这类 bug 查起来非常费劲。

### 3. 所以它待在视觉线程里，不是主循环里

"检测了几次"这件事只有视觉线程知道（主循环看到的是帧）。
放主循环就得把 `detect_every` 的除法抄过去一份 —— 那就是同一个判据写两份实现，
而这个项目在阶段 18 已经因为"同一个排序写两份"吃过一次亏（日志和 OLED 各说各话）。

于是分工是：

```
VisionWorker（视觉线程）
   读帧 → 检测（每 detect_every 帧）→ PresenceTracker.update() → 快照带 obj_counts
        ↓
主循环 20Hz
   把 obj_counts 原样交给 BehaviorEngine.tick()   ← 主循环不碰任何门槛
```

`presence.py` 因此是**纯滤波**：没有时间概念、没有权限概念、不碰硬件、不走网络。
所以自检可以喂任意造出来的序列，一秒跑一万帧。
一旦把"节流"混进去，就没法这么测了。

### 4. 阶段 19 最大的那个坑：**事件会被节流永久丢掉**

"画面里多了个杯子"这件事只发生在那一瞬间。如果按"边沿"表达
（这一帧的 diff 非空 → 报），那么**只要这一刻正好被全局节流拦下，这件事就永远丢了** ——
你放了个杯子，MOSS 一句话不说，而且它自己也不知道自己漏了什么。

这和阶段 16 `leave` 踩过的坑是**同一个毛病**，只是换了个触发源
（当时是"它转过头去看你，人走了却再也不转回来"）。

解法沿用同一招，而且更彻底 —— **账本放在行为层，只有"真的动了"才结账：**

```
_announced   = 上次宣布过的计数     {"cup": 1}
当前计数     = 这一帧的稳定计数     {"cup": 2}
待办 diff    = 当前 − _announced    {"cup": +1}

被节流拦住 → **不结账** → 下一帧看到的 diff 还是那个 → 节流一过自动补上
```

两个好处：

1. **不会丢。** 拦住只是把"结账"推迟，待办不会蒸发。
2. **天然幂等。** 20Hz 的循环里同一件事被看一百遍也不会报一百遍，
   因为第一遍报完账就平了。（而这正是 `arrive` 当年缺的那一环。）

还有一个推论值得单独说：**待办是"账没结清"这个状态，不是一串事件。**
如果存的是事件队列，那"杯子拿走 → 又放回来"会积两条，消费时还得判断它们
是不是互相抵消了。而净额会自己抵消 —— 这一类"配对/取消"的逻辑一行都不用写。

`--autonomy off` 时账本**照常同步**（只是不产生待办）。
不同步的话，你从 off 切到 l0 的那一瞬间，它会补报一串"陈年旧事" ——
跟 `_prev_faces` 那边是同一个道理。

### 5. 权限分级：**注意到了 ≠ 要开口**

分界线仍然是"会不会发出声音"（阶段 16 定的），而"东西变了"天然横跨两档：

| 权限 | 它做什么 | 你听到什么 |
|---|---|---|
| `l0`（默认） | 灯环闪一下青绿 `LED 0 255 160 700` | **什么都听不到** —— 它注意到了，但不打扰你 |
| `l1` | 上面那条 + 说一句"我注意到画面里多了 1 个杯子。" | 一句话 |

`l0` 那一档很重要：它意味着"注意到"和"开口"是两件事。
统计里这两件事也是分开记的 —— `blocked_say`（灯闪了、话没说）和
`blocked_perm`（连灯都没闪）是**两种不同的受限**，混在一起的话，
用户看到"权限不够 5 次"根本不知道该给你哪个建议。

### 6. 措辞：只说它真的知道的东西

```
多了 1 个杯子、少了 1 个瓶子        ← 对
多了 1 个杯子（在你桌上、是你放的） ← **不行**
```

检测器给不出方位、归属、原因。而这句话很可能被原样念出去（还会写进对话历史），
所以 `presence.describe()` 里有一组断言专门盯着这个：句子不许出现
"桌上""手里""你放""因为"。

另外两个细节都是实测跑出来才发现的：

- **同一个类连着变两次，不能是同一句话。** 桌上先有 1 个杯子（说"多了 1 个杯子"），
  20 秒后你又放 1 个（还说"多了 1 个杯子"）—— 两句都是真的，但听起来是复读机，
  而 notice 的 15 秒冷却挡不住这种间隔。修法是**带上总数**：
  第二句变成"多了 1 个杯子，现在 2 个杯子"。第一次**不加**（0→1 时"多了 1 个"
  和"现在 1 个"是同一件事）。"少了"同理：还剩就报"还剩 N 个"，一个不剩就干脆不加。
- **OLED 短标签按字符数截断，不是按个数。** 那句话是给耳朵的，
  屏幕上只有 23 个字符的位置（固件 `char gLine1[24]`）。
  `+cup +keyboard +laptop` 正好 22 个字符；但 COCO 里有 `dining table`
  这种长名字，只卡个数的话两个长名字就能把位置挤爆 ——
  固件那边是**硬截断**的，屏幕上会出现半截单词。
  放不下时尾巴用 `&N`（`+dining table &1`）：**不能用 `+N`** ——
  实测第一版打出来的是 `+cup +keyboard +1`，那个 `+1` 会被读成
  "又多了一个杯子"，而它其实是"还有 1 样别的东西"。

一个附带效果：这个短标签会**临时顶掉** OLED 上那行状态字
（`face x1 + cup, laptop` → `+cup +keyboard +laptop`），
直到下一次 `MODE` 变化才被刷回来。这是有意的 ——
它显示的是"它刚刚注意到了什么"，比一行静态状态更有信息量；
而且**只换 TEXT、不动 MODE**，所以状态机那边一点没受影响。

### 7. "人"不走这条路

`person` / `face` 由 `arrive` / `leave` 管（阶段 16）。
物体事件把它们**排除掉**（`presence.NEVER_ANNOUNCE`），否则一个人走进来
会同时触发"有人来了"和"画面里多了 1 个人" —— **同一件事说两遍**。
这个坑阶段 18 在 `look` 工具上已经踩过一次（YOLO 模式下"1 个人"被说了两遍）。

同一张表里还有**家具/固定物**（椅子、沙发、桌子、电视、盆栽……）。
它们的位置本来就不动，报"沙发来了"是纯噪音；而且它们恰恰是 yolov8n
误报最多的类（阶段 18 实测 `dining table 0.39`、`book 0.44`）——
越是本来就该在那儿的东西，越容易被"认出来"，越不该报。

表里**没有**的类一律算值得报：将来换一个自己微调的模型，
它的类名不在 COCO 里也应该默认能用，而不是被一张写死的表挡在门外。

### 8. 怎么验证

三层，从纯逻辑到整条链：

```bash
# ① 滤波层自检（6 组，不需要摄像头、不需要模型、不需要网络）
python presence.py

# ② 行为层自检（8 组；后两组就是阶段 19 的）
python behave.py

# ③ 端到端探针：A 滤波层 / B presence→behavior 接缝 / C 真起一个 moss_brain 进程
python tools/objects_e2e.py            # 约 25 秒（C 要起子进程）
python tools/objects_e2e.py --no-chain # A+B，两秒跑完
```

`tools/objects_e2e.py` 里最值钱的两条断言：

- **B1**：一串"每 3 次漏 1 次"的检测，原始结果翻转了 **20** 次，
  而行为层只开口 **2** 次。同一组数据里同时给出这两个数 ——
  用来证明"2 次"不是因为这串数据本来就只变了 2 次，而是**滤波真的在干活**。
- **B5**：抖动里夹着**真**变化（1 个 → 2 个 → 1 个 → 0 个），
  4 次都得报出来，而且 4 句都不能一字不差。
  这一条同时盯着"漏"和"重"两个方向。

`--demo --vision-model fake` 也能跑（阶段 18 加的那个假检测器正好有
"杯子出现 → 杯子消失"的剧本），但**探针才是能重复跑的那一份**。

### 9. 这一步踩过的坑（都是真的）

| # | 现象 | 真因 |
|---|---|---|
| 1 | 刚够 3 分就被漏检啃回去，**"离开要 7 次"从来没生效过** | 确认在场时没把分数顶到上限 → 两个门槛互相削弱，等于只剩一个 |
| 2 | 杯子闪一下就"不见了" | 漏检帧（`n==0`）被当成了"个数变成 0"。**在场与否归分数管，个数只从"确实看见了的帧"里取** —— 两件事不要互相越权 |
| 3 | 收尾统计打"新出现 5 · 消失 4"，可它只开过 2 次口 | 暖机期间的"进入"也被计进了 `appear`。原来注释写的理由是"内部记账"，其实没有任何地方用它 —— 改成暖机期间不计（那两个数本来就该是"它报了几次"） |
| 4 | 同一句话连说两遍 | "多了 1 个杯子"在 0→1 和 1→2 时字面一样。带总数解决 |
| 5 | OLED 上出现 `+cup +keyboard +1`，歧义 | `+1` 会被读成"又多了一个杯子"。改成 `&N` |
| 6 | 探针报"设备什么都没收到"，串口看着是通的 | 假设备是被管道读的，Python 按块缓冲 stdout，而最后是 `terminate()` 掉的 → 回显全丢。**而且真机调试时那些回显其实是 `moss_brain` 自己打印的**，根本不该去读子进程管道 |
| 7 | 探针 A1 断言 `visible()=={"cup":1}` 却红了 | **断言写错**：我喂了 `+ flat(26, [])` 之后才断言 —— 那 26 次漏检本来就**该**让它判"走了"。断言写错和代码写错，看起来一模一样 |
| 8 | 探针 A3 算出"进入要 33 次" | 我又一次把暖机当成会影响 `visible()` 了。暖机只影响"报不报变化"，不影响"在不在场" |

第 6、7、8 条都不是产品代码的问题，是**验证工具**的问题 ——
这个项目的原话是：**夹具造假，测出来的结论就是假的。**

### 10. 性能（本机实测）

| 项 | 数字 |
|---|---|
| 滤波 + 对账 + 短标签 | **0.0176 ms / 次检测** |
| 对比：目标检测一次 | 50~70 ms |
| 占比 | **0.03%** |

基本是白送的。它跑在视觉线程里，跟在检测后面，不占主循环的时间。

**默认参数下的反应延迟**：`leave_hits=7` 次漏检。`detect_every=3`、30fps 时
约 **0.7 秒**；`detect_every=1` 时约 **0.23 秒**。
这个延迟是刻意留的（见第 2 节"宁可迟钝，不许撒谎"）。

## 八、排错

| 现象 | 原因 | 修法 |
|---|---|---|
| `打不开画面来源` | 摄像头被占用/编号不对 | 换 `--vision-source 1`，或先 `--demo` |
| `打不开声音来源` | 麦克风选错接口（数字静音） | `python moss_brain.py --auto` |
| 一直是 `IDLE` 不响应声音 | 门限太高 / 房间太安静 | 调低 `--db-th`，或说大声点 |
| 有脸但从不进 `SPEAK` | 听觉没触发（见上一条） | 先单独跑 `pc_audio` 确认麦克风有信号 |
| 状态乱跳 | `--stable` 太小 | 调大到 `6` |
| 预览窗卡顿 | 分辨率太高 | 加 `--width 480 --height 360` |
| `串口连接失败` | 端口没人监听 / 被别的程序占用 | 确认 Wokwi 仿真已启动且面板可见 |
